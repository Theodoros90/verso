# File upload step Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in operator uploads one file to a published workflow that starts with the File upload step; Verso checks it, stages its bytes in the database, starts a run whose input is a reference to the file (plus the text for `.xml` / `.csv`), and the Worker moves the bytes into the document store when the step runs.

**Architecture:** The API receives the multipart upload and never touches the document store: it validates, writes one `ingestion.Uploads` row (bytes in `varbinary(max)`) and submits the run through the existing `ExecutionService.SubmitAsync`. The engine's `file-upload` step (Worker) copies the bytes into the store under a generated staging key and clears the database copy. A Worker background pass clears expired, unused uploads. One migration (new table), no new package.

**Tech Stack:** .NET 10, EF Core 10, ASP.NET Core minimal API (multipart), React + TypeScript, xUnit, Vitest, Playwright E2E.

**Spec:** [docs/adr/0023-file-upload-step.md](../../adr/0023-file-upload-step.md) (owner approved 2026-11-24 with the defaults: database staging, signed-in users only, no malware scanning, PDF/XML/CSV/JSON/TXT/PNG/JPG, 25 MB ceiling, 24 h retention, one file per upload). Code to copy patterns from: `FolderIngestion.SubmitAsync` (submits a run from a file; `folder:` idempotency key), `ExecutionService.SubmitAsync`, `ExecutionEndpoints` (policy, rate limit, size limit), `FolderInputService` (Worker background pass), `DocumentKeys.Staging`, `NodeCatalog` (`file-upload` node, `UploadSizes`, `Uploaders`), `GraphValidator`, `IngestionConfigurations`.

## Deviations from the ADR text (decided while planning, confirm at review)
- **Idempotency:** the ADR said the key is `upload:` + SHA-256 and a caller may send `Idempotency-Key`. The plan keeps the observable behaviour (same file to the same workflow returns the first run, HTTP 200) but implements it with a unique index on `(WorkflowId, Sha256)` and the run key `upload:<uploadId>`; callers do not send `Idempotency-Key` on uploads. Reason: `SubmitAsync` treats a reused key with a different input hash as a conflict, and the run's input contains the new upload id.
- **Largest file** setting: the options become `1mb`, `10mb`, `25mb` (the `100mb` option is removed because it is above the 25 MB ceiling). **Who can upload** keeps only `staff` (`portal-customers` and `anyone-with-link` are out of scope). Already published versions that hold the old values stay valid and immutable; the endpoint clamps the size to the ceiling and answers `upload.not_available` for a non-`staff` value.

## Global Constraints
- Only the Worker writes `IDocumentStore`; the API never calls `WriteAsync` (`DocumentStoreRegistration` comment, CLAUDE.md).
- Storage keys are generated by Verso (`DocumentKeys.Staging`), never from the client's file name; the original name is metadata, sanitised with `DocumentNames.FileName` before it is shown or stored in the payload.
- A run's input is JSON of at most 1,000,000 characters (`ExecutionService.MaxDataChars`); bytes never travel inside it. Global API body cap is 2 MB (`Limits:MaxRequestBodyBytes`); only the upload route raises it, to the file ceiling plus 1 MB multipart overhead.
- Ceiling `Limits:MaxUploadBytes` default 26,214,400 (25 MB); `Uploads:Retention` default 24 hours; `Limits:UploadsPerMinute` default 30 per signed-in user.
- Accepted types (fixed list, case-insensitive extension + leading-byte check): PDF (`%PDF-`), XML and CSV and TXT and JSON (well-formed UTF-8, no NUL byte), PNG (`89 50 4E 47 0D 0A 1A 0A`), JPG (`FF D8 FF`). Client content type is ignored.
- Who may upload: `Policies.Operate` (Operator, Admin), the same people who may submit runs. No anonymous or portal upload.
- File content never appears in logs, events, step results, audit, DTOs or error messages. Audit `FileUploaded` `{ uploadId, workflowKey, fileName (sanitised), size, sha256 }` and `FileUploadRejected` `{ workflowKey, rule }`.
- Migration `FileUploads` creates a new table only. Never run `dotnet ef database update` against anything but throwaway test databases.
- No new package. Synthetic files only (`tests/fixtures`).
- Use `-c Release` for dotnet commands and run `Verso.Api.Tests` classes one at a time with their own `--filter` (several classes in one process fail unrelated `PdfPreviewApiTests`; never run the slow LocalDB class `DatabaseWrite`). Run frontend tests from PowerShell (`cd src/verso-web; npx vitest run --maxWorkers=3`), not Git Bash.
- Commit on branch `feature/file-upload-step` created from `main`; never push; add only your own files by name (never `git add -A` or `.`); leave `docs/superpowers/plans/2026-11-16-document-categories.md` and `tools/db/dummy-customer-contacts.sql` untracked and untouched; never `git stash` or `reset`.

## Review Focus
- A PDF renamed `.csv`, a `.xml` that is not valid UTF-8, an empty file, a file one byte over the limit, a `.exe` renamed `.pdf`: refused with a plain reason, nothing stored, `FileUploadRejected` audited.
- A file name with `..`, `\`, `/`, a device name (`con.pdf`), 300 characters or control characters: never reaches a path or the payload unsanitised.
- The same file uploaded twice, and two identical uploads at the same instant: one run, the second answer is the first run (200, not 202).
- A body larger than the limit that lies about its length, or never ends: stopped while streaming at limit + 1, not buffered whole.
- An upload for a workflow that is inactive, unpublished, does not start with File upload, or whose step says a non-`staff` uploader: `upload.not_available`, no row left behind.
- A run whose upload expired before the Worker took it: fails with `upload.expired`, never starts with empty bytes; a crash after copying but before clearing the row: the re-run succeeds without a second copy.
