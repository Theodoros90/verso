# Fetch from API step (Phase 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workflow step "Fetch from API" sends one GET to an API connection from Configuration (path and query values built from the run data, URL-encoded), and merges the JSON answer into the run data.

**Architecture:** Same shape as the database steps. The engine calls a new `IApiFetch`; `ApiFetchService` (Application) resolves the connection (active, host allowed, secret decrypted in memory) and hands the request to `IApiFetchSender` (Infrastructure, `HttpClient`), which reuses the guards the connection test already has (https only, no redirects, blocked-address check at connect time, TLS 1.2/1.3, auth kinds incl. OAuth client credentials) through a shared helper extracted from `HttpApiProbe`. Worker only. No migration, no new package. Send to API (changing calls) is Phase 3b with its own plan.

**Tech Stack:** .NET 10, `HttpClient`/`SocketsHttpHandler`, System.Text.Json, React + TypeScript, xUnit, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-20-fetch-api-step-design.md` (approved 2026-11-20). Existing code to build on and copy patterns from: `HttpApiProbe`, `IpGuard`, `ApiUrls`, `ApiConnectionService` (`ApiConnectionTestRunner`), `ApiConnectionModels.cs`, `DatabaseQueryService`, `ExecutionEngine.QueryDatabaseAsync`/`RestoreAsync`/`FailRestoreAsync`, the `query-database` node, validator and form pieces, `docs/adr/0017-api-connections.md`, `docs/adr/0019-query-database-step.md`.

## Global Constraints
- GET only: no body, no custom headers (only `Accept: application/json`, `User-Agent: Verso-fetch/1.0` and the connection's own authentication), no redirects followed, no cookies.
- The host is fixed by the connection: the step supplies only a path template and query values. The path template starts with a single `/` (never `//`), has no spaces, control characters, backslash, `?` or `#`, max 500 characters; `{{data.path}}` pieces are valid dotted data paths whose resolved values are **URL-encoded as one piece** (a `/`, `?`, `..` or `%` in a value can never add a segment or change the host). Query lines are `name = data.path` (max 20; names `^[A-Za-z0-9_.\-\[\]]{1,64}$`, no duplicates; names and values URL-encoded). Only text, numbers and true/false data values are accepted (objects/arrays → `query.parameter_invalid`-style issue, missing/null → missing-value issue naming the path, never the value).
- Limits: `maxResponseKB` default 64, 1..256 (service clamps again); `timeoutSeconds` default 15, 1..60 (clamped again). The answer is read at most `maxResponseKB`+1 bytes: more → `api.response_too_large`. Required: JSON content type (`application/json` or `+json`) and valid JSON, else `api.not_json`.
- Outcomes: 2xx with a JSON body → port `found` and the JSON merged at the top level under `resultName` (default `api`, same rules as Query database, not `iteration`; a field of that name is replaced); HTTP 404, or an empty body (204 or a 2xx with no content) → port `not-found`, data unchanged; missing/non-scalar data value → port `failed` (run Rejected `data.fetch_invalid`, nothing sent); every other outcome fails the step.
- Retry: **retryable** are `api.timeout`, `api.unreachable`, `api.server_error` (5xx), `api.rate_limited` (429); everything else is not (`api.unauthorized`, `api.client_error`, `api.redirect_not_followed`, `api.certificate_untrusted`, `api.blocked_address`, `api.host_not_allowed`, `api.token_failed`, `api.secret_unreadable`, `api.connection_unavailable`, `api.not_json`, `api.response_too_large`, `api.bad_request`).
- Never put the answer, the request address (it can hold values and a query key), headers or a secret in a log, event, audit entry, step result or message. Step result: `{ status, durationMs, responseBytes, connection }`. Publish audit: `apiFetches: [{ nodeId, connection, path, queryNames }]` (path template and parameter names, never values). Messages are Verso's own words (`ApiProbeMessages` style), never the API's text.
- Resume: a step that already succeeded with `found` fetches again to rebuild the run data (like Query database); a failure then is `fetch.restore` (retryable per the same table), the step staying Succeeded.
- Worker only; no new package, no migration, no new project. `ApiConnections:AllowedHosts` is honoured for the base host and, for OAuth, the token host (as the test does). The existing probe's behaviour and tests stay unchanged.
- Use `-c Release` for dotnet commands (a stray Verso.Api.exe can lock Debug outputs). Run Verso.Api.Tests classes one at a time with their own `--filter` (several classes in one process fail 8 unrelated `PdfPreviewApiTests` on `main`: pre-existing). No test calls the network: HTTP is faked with a message handler.
- Commit on branch `feature/fetch-api-step`; never push; never `git add` the `.superpowers` folder; never `git stash`/`reset`; leave `docs/superpowers/plans/2026-11-16-document-categories.md` untouched.

## Review Focus
- A data value like `../admin`, `a/b`, `x?y=1`, `%2e%2e`, `a#b` in a path piece or query value stays inside one encoded segment/value and the host never changes.
- A 302 answer is `api.redirect_not_followed`, never followed (no second request).
- A blocked address (loopback, link-local, cloud metadata), a host not in `AllowedHosts`, an unreadable secret: refused with the right code and **no request sent**.
- Non-JSON content type, malformed JSON, an answer over the limit: clear failures, nothing merged.
- The secret and the full request address never appear in logs, events, audit, step result or messages (marker test).
- Retry table: 503 and timeouts retry, 401/400 do not; 404 leaves by `not-found`, not by failure.
- Resume re-fetches and rebuilds the same data; a failing re-fetch is `fetch.restore`.
- The API process cannot resolve `IApiFetch` or the sender.
- The connection test (`HttpApiProbe`) behaves exactly as before.
