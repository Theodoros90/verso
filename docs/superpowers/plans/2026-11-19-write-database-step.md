# Write to database step (Phase 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workflow step "Write to database" runs one author-typed `INSERT`, `UPDATE` or `DELETE` against a Database connection that an administrator switched to "Allow writes", binding values from the run data as parameters, with a row cap and no automatic retry.

**Architecture:** Same shape as Phase 1 (ADR 0019). The engine calls a new `IDatabaseWrite`; `DatabaseWriteService` (Application) resolves the connection (shared with the query service), checks `AllowWrites`, re-checks the text with `SqlGuard.CheckWrite`, and hands it to a per-provider `IProviderWriteRunner` built on a shared `DbWriteExecution` (open, begin, `ExecuteNonQuery`, roll back if more rows than the cap else commit). Worker only. A write step that was started and never recorded as finished is **never started again by Verso**: on resume it fails the run "outcome unknown"; only a person's retry runs it again.

**Tech Stack:** .NET 10, EF Core 10 (one additive migration), Microsoft.Data.SqlClient, Npgsql, MySqlConnector, Oracle.ManagedDataAccess.Core (all already approved, **no new package**), React + TypeScript, xUnit, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-18-write-database-step-design.md` (approved 2026-11-19). Phase 1 code to build on and copy patterns from: `SqlGuard`, `DatabaseQueryService`, `DbQueryExecution`, `SqlServerQueryRunner`, `Verso.Databases/QueryRunners.cs`, `ExecutionEngine.QueryDatabaseAsync`, the `query-database` node and its form pieces, `docs/adr/0019-query-database-step.md`.

## Global Constraints
- One statement, and only `INSERT`, `UPDATE` or `DELETE` as its first word. `UPDATE` and `DELETE` need a `WHERE` at the top level of the statement. No `MERGE`, `TRUNCATE`, DDL, stored procedures, `INSERT ... EXEC`, `SELECT ... INTO`, `INTO` anywhere except once right after `INSERT`. Every other word in `SqlGuard`'s forbidden list stays refused as a bare word, and every dialect-disagreement refusal of Phase 1 (`--` rules, `#`, `/*!`, nested comments, backslash, `$`, prefixed literals, control characters, non-ASCII outside text, ...) applies unchanged.
- Values are driver parameters only (Oracle `:p1..:pN`). SQL max 4,000 characters. `maxRows` (most rows the statement may change) default 1, 1..1000; `timeoutSeconds` default 15, 1..60 (clamped again in the service).
- A connection without `AllowWrites` refuses a write with `db.writes_not_allowed` **before** its password is decrypted or any connection is opened. `AllowWrites` is false by default and for every existing connection; only administrators change it; the audit records the field name, never values.
- Rows affected above the cap: roll back, fail `db.too_many_rows_affected` (nothing changed). Otherwise commit.
- Never retried automatically: every write failure is non-retryable. A failure that may have reached the database (timeout, lost connection, a failing commit, cancellation after sending) carries `OutcomeUnknown = true` and the message "The outcome is unknown: the statement may or may not have changed data. Check the database before running this step again." A server-reported error (constraint violation, permission, syntax) is a known failure: the transaction rolled back.
- A write step is never run again on resume: a Succeeded write step is only replayed (no data to rebuild); a write step found `Running` (crash, or shutdown mid-write) fails the run `write.outcome_unknown`; an operator retry (which resets Failed/Running steps) may run it again.
- Never put values or the SQL in logs, events, audit entries, step results or messages. Step result: `{ rowsAffected, durationMs, connection }` only. Publish audit: SQL text and connection key (`databaseWrites`), never values.
- Worker only (the API never connects or references a runner); no new package or project; migrations are applied by hand: do NOT run `dotnet ef database update` against anything but a throwaway test database (tests create their own).
- Use `-c Release` for dotnet commands (a stray Verso.Api.exe can lock Debug outputs). Run Verso.Api.Tests classes one at a time with their own `--filter`: running several classes in one process fails 8 unrelated `PdfPreviewApiTests` on `main` too (Hangfire static LogProvider; pre-existing).
- Commit on branch `feature/write-database-step`; never push; leave `docs/superpowers/plans/2026-11-16-document-categories.md` untouched.

## Review Focus
- `UPDATE t SET a = 1 DELETE FROM u` (no `;`, SQL Server runs both) and `INSERT INTO t VALUES (1) COMMIT`: refused. `UPDATE t SET a = (SELECT 1 WHERE 1=1)`: refused (the `WHERE` is not top level). `DELETE FROM t` and `UPDATE t SET a = 1` without WHERE: refused.
- Over the cap: a LocalDB test where the statement matches 3 rows with `maxRows` 2 changes nothing.
- `AllowWrites` off: no runner called, no password decrypted (counting runner / unreadable password still gives `db.writes_not_allowed`).
- Worker stop mid-write: the run does not run the statement again; it fails `write.outcome_unknown`; a person's retry runs it once.
- A write step inside For each: iterations that already succeeded are not repeated on resume.
- The parameter marker value never appears in logs, events, audit, step results, the execution DTO or messages (log-capture test as in Phase 1).
- PostgreSQL: the write connection string must not carry `default_transaction_read_only=on` (Phase 1's query connection still does); MySQL `START TRANSACTION` (not READ ONLY).
- Trigger-produced row counts / `INSERT ... OUTPUT`: `ExecuteNonQuery` still works; a statement that returns rows is not an error.
- Turning `AllowWrites` off after publishing: flows fail at run time (`db.writes_not_allowed`, non-retryable), publishing is not blocked.
