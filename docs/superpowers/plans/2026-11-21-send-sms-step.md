# Send SMS step (Phase 4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workflow step "Send SMS" sends ONE real SMS through a transactional SMS connection (Brevo) that an administrator switched on for workflows, to a number and with a text built from the run data, within administrator-allowed country prefixes. Never retried automatically, never repeated by Verso.

**Architecture:** Same shape as the database write and Fetch from API steps. The engine calls a new `ISmsSend`; `SmsSendService` (Application) resolves the connection (active, host allowed, **switch on, transactional, prefix allowed**, key decrypted only after those checks) and hands the request to `ISmsSender` (Infrastructure, `HttpClient`) that reuses the shared outbound guards (`ApiHttp.CreateHandler`: https only, no redirects, blocked addresses at connect time, TLS 1.2/1.3) and ONE deadline over the POST plus the body read. The step is a "changes the outside world" step: the Running-step guard, the shutdown exemption, the non-retryable timeout and the loop-fingerprint protection of ADR 0020 are generalised from the write step to a set of such steps. Worker only. One migration, no new package.

**Tech Stack:** .NET 10, EF Core 10 (one additive migration), `HttpClient`/`SocketsHttpHandler`, React + TypeScript, xUnit, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-21-send-sms-step-design.md` (approved 2026-11-21). Code to build on and copy patterns from: `BrevoSmsProbe`, `SmsConnection` (Domain), `SmsConnectionService` / `SmsConnectionModels.cs` (`SmsRules.TryNormaliseRecipient`, `SmsConnectionSettings`, `SmsConnectionOptions`), the Write to database step (`write-database` node, `DatabaseWriteService`, `ExecutionEngine.WriteDatabaseAsync`, `FailUnfinishedWriteAsync`, `LoopWrites`, the `AllowWrites` switch and its UI) and Fetch from API (`ApiFetchService`, `HttpApiFetchSender`, one deadline), `docs/adr/0018-sms-connections.md`, `0020-write-database-step.md`, `0021-fetch-api-step.md`.

## Facts from Brevo's current documentation (read by the controller on 2026-11-21; re-check before relying on them)
- The documented send endpoint is `POST https://api.brevo.com/v3/transactionalSMS/send`; the existing `BrevoSmsProbe` posts to `/transactionalSMS/sms` (the older path). **Unresolved: which path the live API accepts for this account.** Both the probe and the new sender must use ONE shared constant (`BrevoSms.SendPath`, currently `/transactionalSMS/sms`, unchanged); the ADR records the discrepancy and the owner's manual check (Test connection from the app) tells whether it works; switching to `/send` is then a one-line change.
- Body fields: `recipient` (6 to 15 digits, optional `+`; the probe sends digits only), `sender` (required), `content`, `type` (`transactional`|`marketing`, default transactional; a stop code in the content switches the message to marketing), `unicodeEnabled` (default false), `organisationPrefix`, `tag` (a string or up to 10 strings; **maximum length and allowed characters are NOT stated**), `webUrl`, `templateId`, `params`.
- No idempotency header or parameter is documented for SMS. A 400 `code` list includes `not_enough_credits`, `Insufficient credits`, `invalid_parameter`, `duplicate_request`, `Request already processed`, `unauthorized`, `permission_denied`, `account_under_validation`. 201 with `messageId` (long) is success; `smsCount`/`remainingCredits` are NOT documented for this endpoint (treat as optional). 429 for rate limits. Content over 160 characters is sent as several messages (part sizes are not documented).

## Global Constraints
- One SMS per step execution, to ONE recipient. `to` is a template resolved from data; the resolved value goes through `SmsRules.TryNormaliseRecipient` (international format, 8..15 digits) and must start with one of the connection's allowed country prefixes (digits, no `+`; stored as a comma-separated list, each 1..4 digits, max 20 entries, normalised, max 200 characters; an empty list allows NO country).
- `text` is a template with `{{data.path}}` pieces (dotted data paths via the shared path pattern); pieces are inserted as plain text (scalars only: text, numbers in invariant culture, true/false); a piece that is missing/null → `sms.value_missing`; object/array → `sms.value_invalid`; control characters other than `\n` (and CR before LF), lone surrogates, an empty result, or a result over 480 characters → `sms.text_invalid`; the number: missing/invalid format/outside the allowed countries → `sms.recipient_invalid` / `sms.country_not_allowed`. ALL of these are data issues (never the value in the issue, only the path or rule) → port `failed` → run Rejected `data.sms_invalid`, nothing sent. When the connection has Unicode OFF and the text has a character outside the GSM 7-bit basic set → known failure `sms.text_needs_unicode` (technical, nothing sent).
- Allowed only on connections that are active, `MessageType == transactional`, `AllowSending == true` and have a non-empty allowed-prefix list: otherwise `sms.sending_not_allowed` / `sms.marketing_not_allowed` / `sms.country_not_allowed`, refused BEFORE the key is decrypted and before any request. Host check (`SmsConnections:AllowedHosts`, `sms.host_not_allowed`) also before the decrypt.
- Never retried automatically: EVERY failure is non-retryable. Failures before the request left (data, switch, prefix, marketing, key unreadable, host not allowed, blocked address, name-resolution/connect/TLS-handshake failures, HTTP 400/401/402/403/429 answers) are *known* (nothing sent). After the request left: a timeout, a connection lost, an HTTP 5xx, an unreadable answer, a 400 `duplicate_request`/"already processed" → **outcome unknown** with the fixed wording "The outcome is unknown: the message may or may not have been sent. Check the SMS provider's log before running this step again." A 2xx is `sent` even when the body cannot be read (message id then empty).
- Never repeated: a send step found Running fails the run (`sms.outcome_unknown`; the write step keeps `write.outcome_unknown`); shutdown mid-step leaves it Running; the run/step timeout is a non-retryable unknown failure; a Succeeded send is only replayed on resume (no request); a For each whose loop contains a send step fails `loop.items_changed` if its list changed before a resume (extends ADR 0020).
- Privacy: the number and the text never appear in logs, events, audit, step result, messages, issues or the execution DTO; records override `ToString`. Step result `{ messageId, smsParts, durationMs, connection }` (parts and id optional/null when the answer lacks them). Run-time audit `SmsSent` `{ executionId, nodeId, iteration, connection, messageId, smsParts }` written with the step success (same SaveChanges). Publish audit `smsSends: [{ nodeId, connection, to, text }]` = the TEMPLATES (placeholders and fixed words), never data values.
- `tag`: `verso-` + the first 12 hex characters of the execution id + `-` + the iteration number (only `[A-Za-z0-9-]`, max 24 characters; no personal data), because Brevo documents `tag` but not its limits; if Brevo ever refuses it (400 `invalid_parameter`), the message is NOT retried without it (never retried): the ADR documents it.
- Worker only; the API never sends SMS. One additive migration `SmsConnectionSending` (columns `AllowSending bit NOT NULL DEFAULT 0`, `AllowedCountryPrefixes nvarchar(200) NOT NULL DEFAULT ''`); do NOT run `dotnet ef database update` against anything but throwaway test databases. No new package. The connection test (`BrevoSmsProbe`) behaves exactly as before (one shared path constant).
- Use `-c Release` for dotnet commands (a stray Verso.Api.exe can lock Debug outputs). Run Verso.Api.Tests classes one at a time with their own `--filter` (several classes in one process fail 8 unrelated `PdfPreviewApiTests` on `main`; `LocalFolderAccessTests.AccessDenied_IsReportedWithTheServiceIdentity` fails in this environment: both pre-existing/environmental; never run the slow LocalDB class `DatabaseWrite`). The frontend runner in the main folder is unreliable on this machine (setup failures, 5 s timeouts on connection-dialog tests): use `npx vitest run --maxWorkers=3`; if files still fail at setup, run them in a clean git worktree with a junctioned `node_modules` (and remove it afterwards).
- Commit on branch `feature/send-sms-step`; never push; ONLY your own files BY NAME (never `git add -A`/`.`); leave `docs/superpowers/plans/2026-11-16-document-categories.md` untracked and untouched; never `git add` the `.superpowers` folder; never `git stash`/`reset`.

## Review Focus
- A number or text containing control characters, ` `, lone surrogates, an overlong text, an alphabetic "number", `00357...`, `+357 99 000000`, a number in a disallowed country, `{{x}}` resolving to an object: never reaches the provider, Rejected, no number/text in any issue.
- The switch off / marketing / no prefix / host not allowed / unreadable key: refused with no request and, for the first three, without decrypting (wrong master key still yields the switch error).
- A send step found Running, a shutdown during the request, a step timeout, a lost connection after send, 5xx, duplicate_request: outcome unknown, no retry, never sent again by Verso; an operator retry sends once.
- A For each over a changed list with a send step: `loop.items_changed`, nothing sent twice.
- The number/text/key/tag-with-secret never in logs/events/audit/results/messages/DTOs (marker tests); `ToString` redaction.
- The probe's behaviour and its tests unchanged; the write and fetch steps unchanged.
- The API process cannot resolve `ISmsSend`/`ISmsSender`.
