# Send SMS step (Phase 4): design

Date: 2026-11-21. Status: **awaiting owner approval**. Will become ADR 0022. Builds on ADR 0018 (SMS connections, Test connection sends one real SMS), ADR 0020 (Write to database: the never-retried / never-repeated machinery) and ADR 0021 (Fetch from API: the shared outbound HTTP guards); branch `feature/send-sms-step`, started from `main` (Phases 1 to 3 are merged and pushed).

## Intent
A workflow can send a real SMS to a customer during a run: for example, after parsing the XML, an individual customer gets an SMS and a corporate customer gets an email (the original flow). The step takes the phone number and the message text from the run data and sends one message through an SMS connection from Configuration (Brevo).

## Needs the owner's explicit approval
CLAUDE.md allows real SMS only from **Test connection, to a number an administrator types** (ADR 0018). This phase would let a **workflow author's step send a real SMS to a number that comes from data**. That is a new kind of side effect (it reaches a person's phone, costs a credit, cannot be recalled) and needs your explicit approval, recorded in ADR 0022 and CLAUDE.md.

## Owner decisions already taken
- Anyone who can edit a workflow may author steps that use connections.
- Steps that change the outside world are never retried automatically and never repeated by Verso (ADR 0020), and are switched on per connection by an administrator.

## Goals
- New step **Send SMS** (`send-sms`, category output): settings `connection` (SMS connection key), `to` (a text template resolved from data, for example `{{customer.mobile}}`), `text` (a message template with `{{data.path}}` pieces).
- Ports: `sent` (Brevo accepted the message) and `failed` (a data fault only: missing or invalid number, missing value in the text, text too long, number outside the allowed countries; the run ends Rejected `data.sms_invalid`, nothing sent). Every other failure fails the run (see Retry).
- Step result (visible to every execution reader): `{ messageId, smsParts, durationMs, connection }`: no number, no text.
- A per-connection switch **"Allow workflows to send"** (administrators only, off by default, audited, migration) and a per-connection list of **allowed country prefixes** (administrators, for example `357, 30`). A connection that is switched off, or has no allowed prefix, refuses to send (`sms.sending_not_allowed`) before the key is decrypted and before any request.
- Workflows may use **transactional** connections only in this phase; a marketing connection is refused (`sms.marketing_not_allowed`): marketing needs consent and opt-out wording that Verso does not manage.
- The run-time audit records each accepted message: `SmsSent` `{ executionId, nodeId, iteration, connection, messageId, smsParts }` (no number, no text).

## Non-goals
- No marketing sends, no scheduling, no delivery reports or status tracking, no unsubscribe handling, no per-day or per-month volume cap (see Risks), no other providers, no attachments or links tracking, no replies.
- No automatic retry and no "send once only" ledger table (the engine's step guard gives the never-repeat rule, as for database writes).

## Anti-goals
- A step must never send to a country the administrator did not allow, never send twice without a person deciding, never put the number or the text in a log, event, audit entry, step result, message or execution DTO, and never send a data value that is not clean text.

## Design
1. **Template resolution (design time and run time).** `to` is one placeholder-or-text template; the resolved value goes through `SmsRules.TryNormaliseRecipient` (international format, 8 to 15 digits, Phase ADR 0018 rules) and must start with one of the connection's allowed country prefixes. `text` is a template whose `{{data.path}}` pieces are inserted as plain text (scalars only; numbers in invariant culture); control characters other than a line break are refused; maximum 480 characters after resolution (three parts); when the connection has Unicode switched off and the text needs it (a character outside the GSM 7-bit set), the step fails `sms.text_needs_unicode` without sending (known failure; an administrator can switch Unicode on). All of these data faults are issues naming the data path or the rule, never the value, and end the run Rejected `data.sms_invalid`.
2. **Switch and prefixes.** `connections.SmsConnections` gains `AllowSending` (bit, default 0, existing rows off) and `AllowedCountryPrefixes` (text, comma-separated digits, max 200 characters; empty means none allowed). Administrators change them on the Connections page (the switch asks for confirmation); changes are audited as field names, plus a dedicated `SmsConnectionSendingChanged` entry. The options endpoint for workflow authors returns `[{ key, name, messageType, allowsSending }]` (no sender, no prefixes list, nothing secret).
3. **Sending.** `ISmsSend` / `SmsSendService` (Application, Worker only) resolves the connection (active, host allowed (`SmsConnections:AllowedHosts`), switch on, transactional, prefix allowed), decrypts the key only then, and calls a sender (Infrastructure) that reuses the shared outbound guards (https only, no redirects, blocked addresses at connect time, TLS 1.2/1.3) and the **one-deadline** rule of ADR 0021 (token-less: one POST plus the body read). The request is the one `BrevoSmsProbe` already builds (sender, recipient digits, content, type, unicode flag, organisation prefix) plus a `tag` of the form `verso-{executionId}-{nodeId}-{iteration}` (no personal data) so an operator can find the message in Brevo's own log; the tag is sent only if Brevo's API accepts it (verify against the live API docs when building; if it does not, the tag is dropped and this is recorded in the ADR).
4. **Outcome classification.** Before the request is sent, failures are *known* (nothing sent): bad data, switch off, prefix not allowed, marketing, unreadable key, host not allowed, blocked address, connection refused or DNS failure at connect time, HTTP 400/401/402/403/429 answers (Brevo rejected the request). After the request left, a timeout, a lost connection, an HTTP 5xx or an unreadable answer is an **unknown outcome** (the message may or may not have been sent): the run fails with the wording "The outcome is unknown: the message may or may not have been sent. Check the SMS provider's log before running this step again." A 2xx answer is `sent` even if the answer's body cannot be read (the message id is then empty).
5. **Never retried, never repeated.** The Running-step guard of ADR 0020 is generalised from the write step to a small set of steps that change the outside world (`write-database`, `send-sms`): a step found Running fails the run `step.outcome_unknown` (the existing code `write.outcome_unknown` stays for the write step); a shutdown during the step leaves it Running; a step timeout is a non-retryable unknown failure; a Succeeded step is only replayed. The loop-fingerprint protection of ADR 0020 is extended to loops containing a Send SMS step, so a For each over a list that changed between a first pass and a resume fails `loop.items_changed` instead of sending to the wrong customers or twice. An operator's retry (or a resubmission) can still send a second SMS, which is a person's decision; the runbook says how to check first.
6. **Privacy.** The number and the text exist in the run data (the submitted payload, readable only by auditors and admins) and in the request to Brevo; nowhere else. Messages, issues, events, logs, the step result and the audit never carry them; records that could print them (`SmsSendRequest`) override `ToString`. The publish audit records, per Send SMS node, the connection key and the **templates** `to` and `text` (the placeholders and fixed words, never data values), like the SQL text of the database steps.
7. **Frontend.** A Send SMS node (icon and summary `sms: {connection}`; a visible "sends a message" marker), the connection select with a warning when sending is switched off or the connection is marketing, a text box for the message with a live character and parts counter, a field for the number template; the SMS connection form gets the "Allow workflows to send SMS" switch (with the confirmation sentence "Workflows will be able to send real SMS to numbers taken from their data, within the allowed countries. Each message costs a credit and cannot be recalled.") and the "Allowed country prefixes" field.
8. **Tests.** All HTTP is faked (no test sends a real SMS). Covered: template and number rules, prefix allow-list, marketing refusal, known vs unknown classification, never-repeat paths (Running guard, shutdown, resume, loop fingerprint with a send step), privacy markers in logs/events/audit/results, the switch and the options endpoint, the real service wired into the engine with a fake handler (as for Fetch from API). The first real send is a **manual check by the owner** with the owner's own number, through a switched-on test connection.
9. **Docs.** ADR 0022, CLAUDE.md (milestone line; the safety wording gains the approved Send SMS exception), setup.md (Brevo credit, allowed hosts, allowed prefixes, sender approval rules by country), runbook (what to do after an unknown outcome: search Brevo's log by tag, then retry or not; duplicate-SMS risk), api.md, a sample (the individual vs corporate flow from the XML).

## Risks the owner should know
- **A real message reaches a real person and cannot be recalled.** The guards are the switch, the allowed prefixes, the transactional-only rule, the text limits and the never-repeat rules; none can undo a wrong send caused by wrong data in a correct format and an allowed country.
- **Duplicates after an unknown outcome.** After a timeout the message may have been sent; a person who retries may send it twice. The tag helps to check Brevo's log first.
- **Cost and volume.** A For each over a long list sends one SMS per item (the loop limit is 200 items per run); there is **no daily cap in this phase**. A cap would need a small send log table; recommended later if the volumes grow.
- **Personal data** (phone number, name in the text) goes to Brevo, a third party: the bank's data-protection review must cover it.
- **Any workflow editor can send through any switched-on connection**; the protection is the administrator's switch, the allowed countries and a Brevo account limited to what is needed.
- **Delivery is not tracked:** Brevo accepting the message (2xx) says nothing about delivery to the handset.
- **Nothing is verified against live Brevo in tests.**

## Approaches considered
- **A. A separate Send SMS step with a per-connection switch, allowed prefixes and the never-repeat machinery (proposal).** Same pattern as the database writes; the palette and audit show which steps send messages.
- **B. Reuse Send email with an "SMS" channel option.** One step, but the two channels have different rules (recipient format, length, cost, retries); it hides a change in cost and risk behind a dropdown.
- **C. Send immediately without a switch or allowed prefixes, rely on the administrator's care.** Simplest; rejected: one data mistake could message the wrong country or a premium-rate range.
