# ADR 0023: File upload step (a person uploads a file and starts a run)

- Status: **proposed (draft 2026-11-24), not yet approved, nothing implemented.** On 2026-11-24 the product owner decided three questions: **(1) database staging** for the bytes, **(2) signed-in Verso users only** (no external portal), **(3) no malware scanning**. Questions 4 to 7 below keep the proposed defaults until the owner confirms or changes them; the owner's explicit approval to implement is still needed.
- Today the `file-upload` step is simulated ([NodeCatalog](../../src/Verso.Application/Workflows/NodeCatalog.cs)): its settings are stored and validated, but there is no upload screen, nothing receives a file, and the engine passes the submitted data straight through. This ADR makes it real.
- Builds on [ADR 0001](0001-folder-input.md) (the other real file input; its file-to-run handoff, duplicate rules and `.xml` / `.csv` payload shape are reused) and the document store of plan §7.
- If approved, CLAUDE.md is amended in the same change: the architecture rule moves File upload out of the simulated list, and the "Current milestone" line names this item.

## Context

Folder input lets the Worker pick files up from a server folder. Staff and, later, portal users also need to hand a file to a workflow by hand: "here is today's customer list", "here is a scanned form". The step's settings already exist: **accepted file types** (for example PDF, XML, CSV), **largest file** (for example 25 MB) and **who can upload** (for example signed-in staff). Nothing enforces them.

Three facts in the current code shape the design:

1. **The API never writes to the document store.** `IDocumentStore` is written only by the Worker, and the store's root folder is meant to be writable only by the Worker's service account (`DocumentStoreRegistration`). An upload endpoint in the API cannot simply call `WriteAsync` without breaking that rule.
2. **A run's input is JSON of at most 1,000,000 characters.** The submit endpoint caps its body at 1,100,000 bytes (`ExecutionEndpoints.MaxSubmitBodyBytes`) and the whole API caps bodies at 2 MB (`Limits:MaxRequestBodyBytes`). A 25 MB file cannot travel inside a run's input.
3. **Storage keys are generated by Verso**, never from input (`DocumentKeys`, `LocalFileDocumentStore.KeyPattern`). The same must hold for uploads.

An upload is also the first input that carries **bytes chosen by a person who may not be trusted**, so type checks, size limits, retention and the question of malware scanning matter more than for the other steps.

## Decision (proposed)

1. **The step stays `file-upload`**, category input, port `out`. Its three settings keep their meaning and become **enforced at upload time**. The step is removed from the simulated list in the catalog description, `docs/api.md`, the plan and CLAUDE.md.

2. **New endpoint** `POST /api/v1/workflows/{key}/uploads`, `multipart/form-data`, one file part named `file`. It uses its own request-size limit (the step's "largest file", never above a hard ceiling `Limits:MaxUploadBytes`, default 25 MB), not the 2 MB global one. Checks, in this order, each with a Verso problem code and no echo of file content:
   1. the workflow exists, is published and active, and its start step is a File upload step (`upload.not_available`);
   2. the caller's role satisfies "Who can upload" (`upload.forbidden`);
   3. the body size is within the limit, checked while streaming, never after buffering the whole body (`upload.too_large`);
   4. the extension is one of the accepted types **and** the leading bytes match it: `%PDF-` for PDF, well-formed UTF-8 text for XML and CSV (`upload.type_not_allowed`). The client's content type and file name are never trusted;
   5. rate limit per user, like submissions (`Limits:UploadsPerMinute`).

3. **Where the bytes wait (owner decision 2026-11-24: database staging).** Because of fact 1, the API does not write to the document store. The bytes are staged in the database. A new table `ingestion.Uploads` (Id, workflow, uploader, original name as metadata only, content type, size, SHA-256, `Content varbinary(max)`, status, created, expires) holds the file until a run has taken it. The Worker, when the run starts, copies it into the document store under a generated staging key (`staging/<execution>/<node>.<ext>`, the existing `DocumentKeys.Staging`) and clears the database copy. No change to who may write the store. See the alternatives below.

4. **Starting the run.** The same request creates the execution through the normal submission path (so queueing, idempotency, audit and history are the ones that already exist). The run's input is a **reference, never the bytes**:
   ```json
   { "upload": { "id": "<guid>", "fileName": "customers.xml", "contentType": "application/xml", "size": 18234, "sha256": "…" } }
   ```
   For `.xml` and `.csv` up to the 1,000,000-character data limit, the input also carries `"content": "<text>"` exactly as Folder input does ([ADR 0001](0001-folder-input.md) addenda 3 and 4), so the existing Parse step works unchanged. For anything larger or binary (PDF), only the reference is carried, and a later step reads the file by upload id. The response is `202 Accepted` with the execution, like `POST …/executions`.

5. **No unintended duplicate runs.** The run's idempotency key is `upload:` + the file's SHA-256 + the workflow, unless the caller sends an `Idempotency-Key`. Uploading the same file twice returns the first run (HTTP 200, not 202), as Folder input does for identical data. The page tells the person, so a deliberate re-upload (changed file) works and an accidental double click does not run twice.

6. **The file is data, never code.** It is never executed, opened by a viewer in the API, or written under its original name. The original name is shown in history after the same sanitising as `DocumentNames.FileName`. Only the Worker reads the staged bytes, by id, never by a path from a payload.

7. **Retention.** An upload that no run has taken within `Uploads:Retention` (default 24 hours) is deleted by the Worker, and the audit keeps the hash and size. A staged copy follows the existing staging cleanup.

8. **Audit and logs.** New audit events `FileUploaded` (who, workflow, file name after sanitising, size, SHA-256) and `FileUploadRejected` (who, workflow, rule that failed). File content never appears in logs, events, results, DTOs or the audit.

9. **Frontend.** An upload dialog on the workflow page (visible only for a published workflow that starts with File upload and only to roles allowed to upload): drag and drop or choose, shows the allowed types and size from the step, shows progress, and links to the new run in execution history, whose live progress already exists (M8). A rejection shows the plain-language reason. `.doc` / `.exe` and other types not listed are refused before sending when the browser can tell, and always again by the API.

10. **Designer.** The three settings get design-time checks: at least one accepted type from a fixed list (`PDF`, `XML`, `CSV`, `JSON`, `TXT`, `PNG`, `JPG`), a size between 1 KB and `Limits:MaxUploadBytes`, and a "Who can upload" value from the existing role names. The step description loses the word "Simulated".

11. **Contracts and tests.** OpenAPI snapshot and generated frontend types regenerated; `docs/api.md`, the plan and CLAUDE.md updated in the same change. Tests: unit tests for the type, size and role checks (including a PDF renamed `.csv`, an empty file, a file larger than the limit by one byte, a `.xml` with invalid UTF-8); integration tests for the endpoint on LocalDB (accepted, each rejection, duplicate, retention); a worker test for staging; a browser E2E test of upload, run and history. Migration **`FileUploads`** (new table only, no data loss).

## Alternatives considered

- **Let the API write the file to a second folder** (an uploads root the API's account can write). It avoids the database `varbinary` but gives the web process a writable folder on disk and needs a new root setting, a new permission and cleanup rules. It breaks the "only the Worker writes files" rule; not recommended, but possible if the bank prefers files over database blobs.
- **Let the API write straight to `IDocumentStore`.** Simplest, but it widens the rule that only the Worker's account can write the store, so a flaw in the web process could overwrite archived documents. Rejected unless the owner explicitly changes the rule.
- **Put the bytes inside the run's input.** Rejected: the input is limited to 1,000,000 characters and is stored with the run, so large or binary files cannot fit.
- **A chunked or resumable upload.** Not needed at 25 MB inside a bank network; revisit if limits grow.

## Consequences

- Large `varbinary(max)` rows live briefly in the database. At 25 MB and a modest upload rate this is acceptable, but backups and the transaction log grow with upload volume, and the retention job must run.
- Hosting: IIS needs `maxAllowedContentLength` and the ASP.NET Core module's request limit raised for this one route to the upload ceiling (the runbook is updated); the global 2 MB cap stays for everything else.
- **No malware scanning (owner decision 2026-11-24).** An uploaded file is accepted if its type, size and leading bytes check out. This is a knowingly accepted risk: uploaded files are never opened or executed by Verso, and only signed-in staff can upload, but a harmful file could still pass through to a later step or to a recipient (for example an email attachment). If the bank later requires scanning, it is a new decision (a "quarantined until scanned" status and a scanner choice) and does not change the rest of this design.
- A person can start many runs by uploading. The per-user rate limit and the duplicate rule bound this; there is no per-day cap now (same position as ADR 0022).
- **Signed-in Verso users only (owner decision 2026-11-24).** Portal users outside the bank's staff are out of scope. The upload endpoint requires the normal sign-in; there is no anonymous or token-link upload.

## Open questions for the owner

Decided on 2026-11-24: (1) database staging; (2) signed-in Verso users only; (3) no malware scanning. Still open (defaults apply until answered):

4. **File types.** Is the proposed list (PDF, XML, CSV, JSON, TXT, PNG, JPG) right, and is a ceiling of 25 MB right?
5. **Retention.** Is 24 hours for an upload nobody has used acceptable, and how long may a processed upload's staged copy be kept?
6. **Several files at once.** One file per upload (assumed) or a batch that starts one run per file.
7. **Test data.** Confirmation that all development and test files stay synthetic (`tests/fixtures`), as the rules require.
