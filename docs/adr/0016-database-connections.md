# ADR 0016: Database connections managed in the app (SQL Server, test only)

- Status: accepted (implemented 2026-11-16, awaiting acceptance).
- Requested and approved by the product owner on 2026-11-16: add a SQL Server connection (server, login, password) in Configuration, Connections. Chosen scope: **a real connection with Test connection only; the Database query step stays simulated.** The product owner confirmed the account is **read-only** and the server is **not production**.
- CLAUDE.md listed database access as simulated until approved ("Database query step: no database access"); this ADR records the approval, scoped to opening a connection and running a fixed `SELECT 1`.

## Context

The Connections tab was simulated and browser-only. ADR 0015 added real email relays with an encrypted, write-only password. The product owner wants the same for a database server, so that a later step can use it by name.

## Decision

1. **One flow.** In Connections, **New connection** with the authentication **SQL Server login** switches the dialog to the database form (server name, login, password, optional database, encrypt, trust-certificate, timeout, key) and creates a real connection through the API. Real connections appear as cards in *Data sources* with a switch (on / off), **Configure** and **Test connection**. Only administrators see or create them. Every other connection stays simulated.
2. **Storage.** `connections.DatabaseConnections` (new schema `connections`, migration `DatabaseConnections`): key (unique, same pattern as email relay keys), name, server, database, login, encrypt, trust-certificate, timeout, active, and the encrypted password. Connections are deactivated, never deleted (grants deny DELETE).
3. **The password is write-only and encrypted**, exactly as in ADR 0015: AES-256-GCM, master key `Secrets:MasterKey` kept outside the database (the same key and the same protector), context `database-connection:{key}` so a stored value can't be moved to another row. Never returned, logged, audited, exported or shown; responses carry only `hasPassword`.
4. **Test connection runs on the Worker**, as the email test does (ADR 0015 decision 7): `POST /api/v1/database-connections/{id}/tests` records a row in `connections.DatabaseConnectionTests` (audited as `DatabaseConnectionTestRequested`) and queues a Hangfire job. The Worker decrypts the password in memory, connects with `Microsoft.Data.SqlClient` (already in the project through EF Core: **no new package**), and runs the fixed text **`SELECT 1`**. It never runs any text a person wrote. Read-only intent (`ApplicationIntent=ReadOnly`), no connection pooling, the configured timeout.
5. **No connection-string injection.** The string is built with `SqlConnectionStringBuilder` from validated parts. The server may be a host name or address with an optional `\INSTANCE` or `,port`; characters such as `;`, `=`, quotes and spaces are refused, as they are in the login and database name.
6. **Safe results.** A result holds a status, our own error code and wording (`db.login_failed`, `db.unreachable`, `db.timeout`, `db.cannot_open_database`, `db.password_expired`, `db.certificate_untrusted`, `db.password_unreadable`, `db.server_not_allowed`, `db.test_failed`) and, on success, the server version. It never contains the server name, the login or the password (SQL Server's own message can name them, so it is not passed on).
7. **Encryption on by default.** `Encrypt` is on. "Trust server certificate" is off by default and labelled non-production only; an untrusted certificate fails with `db.certificate_untrusted` and tells the administrator to install the authority.
8. **Optional limit by the administrator.** `DatabaseConnections:AllowedServers` (Worker configuration): when not empty, the Worker connects only to those hosts (case-insensitive, the part before an instance or port). Anything else fails with `db.server_not_allowed` without a connection attempt. Recommended in production, because an administrator otherwise chooses the host the Worker connects to.
9. **Who and audit.** Administrators only. Audited with changed field names, never values: `DatabaseConnectionCreated`, `DatabaseConnectionUpdated`, `DatabaseConnectionPasswordChanged`, `DatabaseConnectionDeactivated`, `DatabaseConnectionActivated`, `DatabaseConnectionTestRequested`. Test rows are deleted after 24 hours (hourly Hangfire job).
10. **Least privilege.** The API may select, insert and update in the `connections` schema; the Worker may select, and update or delete only test rows; nobody may delete a connection; only the API inserts tests.

## Consequences

- **A second credential is now stored by Verso** (encrypted). The bank must accept this and protect the master key, as for email relays. Folder input still stores no credentials.
- **The Worker reaches a database the administrator names.** Use a **read-only login on a non-production server**, and set `DatabaseConnections:AllowedServers` in production. The connection is real, so the Worker server must be able to reach the host (firewall).
- The Database query step is **unchanged and still simulated**. Using a connection in a step, running queries, row limits and personal-data handling need their own ADR (free-form SQL from workflow authors would be user-authored code and is not allowed by the project rules; parameterised or pre-approved queries would be the starting point).
- Only SQL Server is supported (the driver already in the project). Other engines need a new package and approval.
- Not done: using a connection in a workflow step, key rotation, per-connection rate limits.

## Addendum 1 (2026-11-16): PostgreSQL, MySQL / MariaDB and Oracle

- Requested by the product owner ("all SQL that can log in: Oracle, PostgreSQL, MySQL, etc."); the owner approved adding the three drivers below on 2026-11-16 (the answer also ticked "only SQL Server"; read as: keep SQL Server and add the others). The scope is unchanged: **Test connection only** (a fixed `SELECT 1`, or `SELECT 1 FROM DUAL` on Oracle); no step runs a query.
- **Database type.** A connection has a type, chosen on creation and never changed: `SqlServer` (default, also for callers of the earlier contract), `PostgreSql`, `MySql` (MySQL and MariaDB), `Oracle`. The authentication in New connection is now **Database login** (it was SQL Server login). New fields: `provider` and `port` (0 or empty = the type's default: 1433, 5432, 3306, 1521). Migration `DatabaseConnectionProviders` adds both columns; existing rows become SQL Server with the default port.
- **New packages (Worker only, new project `Verso.Databases`, versions pinned in `Directory.Packages.props`, no known vulnerabilities at the time):** **Npgsql 10.0.2** (PostgreSQL licence, permissive), **MySqlConnector 2.6.2** (MIT; chosen over Oracle's MySql.Data, which is GPLv2 with exceptions or commercial), **Oracle.ManagedDataAccess.Core 23.26.300** (Oracle Free Use Terms: **free to use but not open source**; the bank's licence review must accept it). The API never loads them (it does not reference `Verso.Databases`). SQL Server stays in `Verso.Infrastructure` with its driver from EF Core. Layering: `Verso.Databases` references `Verso.Application` only.
- **Probes.** `IProviderProbe` per type; `DatabaseProbeRouter` picks by the connection's type, and a type with no registered driver fails with `db.provider_unavailable`. Every probe builds its connection string with the driver's own builder from validated parts (a hostile password stays one quoted value), no pooling, the configured timeout. PostgreSQL asks for a read-only session; SQL Server uses read-only intent.
- **Rules that differ.** SQL Server's server may carry `\INSTANCE` or `,port`; the others take a plain host and the separate port. Oracle needs a **service name** (in the database field) and builds its connect descriptor from validated parts (TCPS when "encrypt" is on); it has **no trust-certificate switch**: the server certificate must be trusted by the Worker's certificate store or wallet. For the others, encryption verifies the certificate unless "trust the server certificate" is ticked (non-production only).
- **Same safe results.** The same codes and Verso-worded messages for every type (never the driver's text); drivers' errors are mapped by SQLSTATE or error number, and by the exception chain for certificate, network and timeout problems.
- **Not verified against real servers.** The unit and API tests check the rules, the connection strings and the error mapping with no database; the PostgreSQL, MySQL and Oracle probes were **not** run against a live server in this change. Try Test connection against a non-production server of each type before relying on it.
- Not done: other engines (Db2, SQLite and so on), Oracle wallet or Kerberos login, using a connection in a workflow step.
