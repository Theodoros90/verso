# ADR 0022: Send SMS step (one real SMS from a workflow)

- Status: accepted (implemented 2026-11-21, awaiting acceptance).
- Requested by the product owner on 2026-11-21 ("Phase 4, the Send SMS step"). **Explicit approval of the owner on 2026-11-21**: a workflow step may send **real SMS** to numbers taken from a run's data (until now real SMS were allowed only from Test connection, to a number an administrator types, [ADR 0018](0018-sms-connections.md)). The owner took five decisions the same day: (1) **approval** of real SMS from workflows; (2) **allowed country prefixes, deny by default**: a connection with no prefix sends nowhere; (3) **transactional connections only**: marketing is refused; (4) **no daily or monthly cap now** (see Consequences); (5) the branch `feature/send-sms-step` starts **from `main`** (Phases 1 to 3 merged). Earlier owner decisions that apply: anyone who can edit a workflow may author steps that use connections; steps that change the outside world are never retried automatically and never repeated by Verso, and are switched on per connection by an administrator ([ADR 0020](0020-write-database-step.md)).
- Builds on ADR 0018 (SMS connections, Brevo, the encrypted API key), ADR 0020 (the never-retried / never-repeated machinery, now shared) and [ADR 0021](0021-fetch-api-step.md) (the shared outbound HTTP guards and the one-deadline rule). Design: `docs/superpowers/specs/2026-11-21-send-sms-step-design.md`; plan: `docs/superpowers/plans/2026-11-21-send-sms-step.md`.
- CLAUDE.md is amended in the same change: the approved-integrations list names this step, and the architecture rule says the Send SMS step is real.

## Context

A bank flow often has to tell a customer something short: "your statement is ready", "your card has been sent". The motivating flow: an XML file of customers is parsed; an individual customer gets an SMS, a corporate customer gets an email. ADR 0018 lets an administrator store a Brevo SMS connection and send one test SMS; no workflow could use it. A real SMS reaches a person's phone, costs a credit and **cannot be recalled**, so the step must never send to a country the administrator did not allow, never send twice without a person deciding, and never put the number or the text anywhere but the request to Brevo.

## Decision

1. **The step.** `send-sms` ("Send SMS", category output, next to Write to database in the palette), input `in`, ports `sent` (the success exit) and `failed` (optional). Settings:
   - `connection`: key of an SMS connection (the `sms-connection` widget; the schema marks it `x-requires-sending`). Publishing checks only the key's shape: whether the connection exists, is active, is transactional or allows sending is checked at run time.
   - `to`: the number template, 1 to 100 characters: one or more `{{data.path}}` pieces (for example `{{customer.mobile}}`), or a fixed number made of digits, `+`, spaces, dots, dashes and brackets (a fixed number is only character-checked at publish; its format is checked at run time).
   - `text`: the message template, 1 to 480 characters, fixed words with `{{data.path}}` pieces. The fixed part may hold no control character except a line break, no invisible format character (bidi overrides, zero-width space and the like; the zero-width joiner is allowed for emoji) and no lone surrogate.
   - Both templates need balanced `{{ }}` and valid dotted data paths; problems are reported as `config.invalid` on `to` or `text` with Verso's own wording. A blank value is reported once, by the schema's required check.
2. **Building the message (Worker, at run time).** Each piece is replaced by its value as **plain text** (an SMS is not HTML or a URL; a value holding `{{x}}` stays literal): text, a number in the invariant culture, `true` / `false`. Data issues, each naming the data path or the rule and **never the value**:
   - `sms.value_missing`: the value is missing or null;
   - `sms.value_invalid`: a list, a group of fields, or a number no .NET number can hold (such as `1e400`, which .NET 10 reads as Infinity; it is refused rather than written out as "Infinity");
   - `sms.text_invalid`: text that can't be read (a lone-surrogate escape), a value with a control or invisible format character or a lone surrogate, or a finished text that is empty or longer than 480 characters (a CR LF counts as one line feed);
   - `sms.recipient_invalid`: the finished number is empty or is not an international number (`SmsRules.TryNormaliseRecipient`: an optional `+` or `00`, then 8 to 15 digits starting with 1 to 9; spaces, dots, dashes and brackets ignored).
   Any data issue takes the `failed` port **without calling the SMS service** (nothing sent).
3. **Ports and run states.**
   - `sent`: Brevo accepted the message (an HTTP 2xx). The run's data is unchanged. The step result is `{ messageId, smsParts, durationMs, connection }` (`messageId` and `smsParts` are null when Brevo's answer lacks them).
   - `failed`: **only a fault of the data**: the issues of item 2, plus three refusals of the service before anything is sent: `sms.recipient_invalid`, `sms.country_not_allowed` (the number's country is not among the connection's allowed prefixes, **including a connection whose list is empty**) and `sms.text_invalid`. The run then ends **Rejected `data.sms_invalid`** ("The data can't make a valid message in step '…' (see its issues)."). As with every rejecting output except a declined approval, the run ends Rejected **whether or not something is connected to `failed`**; inside a For each this rejects the whole run, and messages already sent for earlier items stay sent. A Rejected run is not retried: the data is fixed and submitted again.
   - **Every other failure fails the run** (Failed, the code below) and is **never retried automatically**. In particular **`sms.text_needs_unicode`** (the text needs a character outside the GSM 7-bit set and its extension table, and the connection has Unicode switched off) **fails the run, it is not Rejected**: it is a setting of the connection, nothing is sent, and an administrator can switch Unicode on before a person retries.
4. **The checks and their order** (`SmsSendService`, Application, Worker only). All are known failures (nothing sent):
   1. the request again: the number (`sms.recipient_invalid`), the text (`sms.text_invalid`), the tag (`sms.tag_invalid`; `^[A-Za-z0-9-]{1,24}\z`);
   2. the connection exists and is active (`sms.connection_unavailable`);
   3. transactional (`sms.marketing_not_allowed`);
   4. the administrator's switch "Allow workflows to send SMS" is on (`sms.sending_not_allowed`);
   5. the number starts with one of the allowed prefixes (`sms.country_not_allowed`; only stored entries of 1 to 4 ASCII digits not starting with 0 count, anything else is ignored, never widened; an empty list allows no country);
   6. the host is in `SmsConnections:AllowedHosts` when that list is set (`sms.host_not_allowed`);
   7. the stored base address is still a valid https address (`sms.bad_request`);
   8. Unicode needed but off (`sms.text_needs_unicode`);
   9. **only then** is the API key decrypted, in memory only (`sms.secret_unreadable` when it can't be). A wrong master key therefore still yields the answers of steps 1 to 8 (tested).
5. **The request** (`HttpSmsSender`, Infrastructure, Worker only, `HttpClient`, no new package). `POST {baseUrl}{BrevoSms.SendPath}` with the headers `api-key`, `Accept: application/json` and `User-Agent: Verso-sms/1.0`, and the JSON body `{ sender, recipient (digits, no "+"), content, type, unicodeEnabled, organisationPrefix (only when set), tag }` built by `BrevoSms.BuildBody`, the **same builder** the connection test uses (its body is byte-identical to before; the test sends no tag). The shared guards of ADR 0017 / 0021 (`ApiHttp.CreateHandler`): https only, no redirects, no cookies, loopback / link-local / unspecified / multicast addresses refused when connecting, TLS 1.2 / 1.3; the finished address must be https on the base address's host and port, without user info or fragment. **One deadline** (the connection's time limit, clamped to 1 to 60 seconds; connections default to 15) covers the POST and the reading of the answer. The answer is read at most 64 KB, only for `messageId` (a string or a number; longer than 100 characters is dropped) and `smsCount` if present, and, on a 400, to tell a duplicate, an empty balance or a bad number apart. It is never stored, logged or shown.
6. **Known and unknown outcomes.** Brevo documents no idempotency key for SMS, so a message whose fate is unclear must never be sent again automatically.
   - **Known (nothing sent):** every check of item 4; a request that could not be built (`sms.bad_request`); `sms.blocked_address`; a failure while connecting (name resolution, TCP connect, proxy tunnel: `sms.unreachable`; TLS handshake: `sms.certificate_untrusted`); and Brevo's refusals: 3xx `sms.redirect_not_followed`, 401 / 403 `sms.unauthorized`, 402 `sms.insufficient_credits`, 429 `sms.rate_limited`, a 400 classified as `sms.insufficient_credits`, `sms.invalid_recipient` (Brevo's own refusal of the number, which fails the run; not to be confused with Verso's `sms.recipient_invalid`, which rejects it) or `sms.client_error`, and any other 4xx (`sms.client_error`, which is also what a wrong send path would give, see item 9).
   - **Unknown (the message may have been sent):** a deadline (`sms.timeout`), a connection lost or a TLS failure after connecting (`sms.connection_lost`), HTTP 5xx (`sms.server_error`), an unexpected final status (`sms.unexpected_answer`), a 400 that says `duplicate_request` or "already processed" (`sms.duplicate_request`), a 400 whose body can't be read, and anything unexpected (`sms.unreachable`, see below). The step's error and the run's message are then the fixed wording: **"The outcome is unknown: the message may or may not have been sent. Check the SMS provider's log before running this step again."**
   - **A 2xx is `sent`** even when its body can't be read, the deadline fires during the read, or the Worker is stopping: the fact that Brevo accepted the message is never lost (the id and parts are then null).
   - **`sms.unreachable` has two meanings, and the message tells them apart:** from the sender it is the known connect failure ("The SMS provider could not be reached. Check the address, the network, the firewall and any proxy."); from the service (an exception thrown by the sender) or from the engine (an exception from the service, or an unexpected failure while the step runs) it carries the unknown wording above. The exception's own text is never kept.
7. **Never retried, never repeated.** The ADR 0020 machinery is generalised from the write step to the steps that change the outside world, `NodeCatalog.ChangesOutsideWorld` = `write-database` and `send-sms`:
   - every failure of a Send SMS step is final (`retryable: false`); the engine's three automatic attempts never apply;
   - the step is saved Running before the call; a step **found Running** when the run is picked up again (the Worker crashed, was killed or stopped mid-send) is not run again: the run fails with **`sms.outcome_unknown`** ("Step '…' was started but never recorded as finished (the Worker stopped or crashed): the message may or may not have been sent. Check the SMS provider's log before retrying."). The write step keeps **`write.outcome_unknown`** and its wording unchanged;
   - a Worker shutdown during the step leaves it Running (it is not interrupted and requeued like other steps), so the next pick-up fails it as above;
   - the run's 5-minute time limit hit during the step is a final `execution.timeout` "…while the message was being sent." followed by the unknown wording (also when the limit happened to fire just before the request: Verso reports the safe side);
   - a Succeeded send is only **replayed** on resume (after an approval, a retry of a later step, a restart), never called again;
   - a **For each** whose loop contains a Send SMS step records a fingerprint of its list and, when a resumed run finds a different list, fails with **`loop.items_changed`** (not retried) before any item runs, with SMS wording ("…matching the list again could skip an item or send one twice. Messages already sent for earlier items were not sent again; no later item ran. Check the SMS provider's log, then submit the data again if needed (a new run sends every item again).");
   - **an operator's Retry, or a new submission, does send again**: that is a person's decision, and the runbook says how to check Brevo's log first.
8. **The tag.** Each message carries `tag = "verso-" + the first 12 hexadecimal characters of the execution id + "-" + the iteration` (0 outside a For each; 1, 2, … for the items inside one), at most 24 ASCII letters, digits and dashes, no personal data, so an operator can find the message in Brevo's log. **It has no node id: two Send SMS steps in the same run (and iteration) share a tag**; the step's time in the run history tells them apart. Brevo documents `tag` (a string or a list) but **not its length or allowed characters**; if Brevo ever refuses it (a 400 `invalid_parameter`), the step fails known `sms.client_error` and the message is **not** resent without the tag (never retried).
9. **The send path is unresolved.** The connection test of ADR 0018 has always posted to `/transactionalSMS/sms`; Brevo's current documentation names `POST /v3/transactionalSMS/send`. Both callers now use **one constant**, `BrevoSms.SendPath`, still `/transactionalSMS/sms` (unchanged, owner ruling). The owner's manual check (Test connection from the app with the owner's own number) tells whether the live API accepts it; if not, the test fails (typically `sms.client_error` for a 404, nothing sent) and switching to `/send` is a one-line change that moves the test and the step together.
10. **Brevo's answer is thin.** The documentation promises only `messageId` (a number) on success. `smsCount` and `remainingCredits` are not documented for this endpoint: `smsParts` is read when present and is otherwise null; the credits are not read by the step.
11. **Administration** (ADR 0018 connections, migration **`SmsConnectionSending`**: two columns on `connections.SmsConnections`, `AllowSending bit NOT NULL DEFAULT 0` and `AllowedCountryPrefixes nvarchar(200) NOT NULL DEFAULT ''`; existing connections are off and allow no country).
    - Administrators only (the SMS connection endpoints stay administrators only) switch **"Allow workflows to send SMS"** on (the Connections page asks for confirmation: "Workflows will be able to send real SMS to numbers taken from their data, within the allowed countries. Each message costs a credit and cannot be recalled.") and type the **allowed country prefixes** (comma, space or semicolon separated; a leading `+` or `00` is dropped; each 1 to 4 digits not starting with 0; repeats dropped; at most 20; stored normalised as `357,30`).
    - Request fields `allowSending` / `allowedCountryPrefixes`: omitted keeps them on update, off / empty on create. The page sends `allowSending` only when the switch was touched, and `allowedCountryPrefixes` only when the field was edited, so an unrelated edit (or a dialog left open while someone else changed the connection) never changes or widens them; a new connection always sends both.
    - Audit: `SmsConnectionUpdated` lists `allowSending` / `allowedCountryPrefixes` among the changed field names; a dedicated `SmsConnectionSendingChanged { key, allowSending }` is written whenever the switch changes (also on create when switched on); the prefixes themselves are not audited.
12. **Who may author, and the options endpoint.** Anyone who can edit workflows may use any SMS connection (owner decision). `GET /api/v1/sms-connection-options` (workflow authors and administrators, mapped outside the administrators' group) returns the active connections ordered by name as `{ key, name, messageType, allowsSending }` and nothing else (no sender, prefixes, base address or secret flag). The designer's dropdown warns when a connection has sending off ("Sending is switched off for this connection. An administrator can switch it on in Configuration, Connections.") or is marketing ("Marketing connections can't be used in workflows.").
13. **Privacy.**
    - The number and the text exist in the run's submitted data (readable by auditors and administrators only) and in the request to Brevo; **nowhere else**: not in logs, events, issues, messages, the step result, the audit or the execution DTO (marker tests cover the execution, events, audit by entity and trace id, and captured logs). `SmsSendRequest.ToString` prints `[redacted]` for the number, the text and the tag.
    - Run-time audit: one **`SmsSent`** entry per accepted message, `{ executionId, nodeId, iteration, connection, messageId, smsParts }` (entity `Execution`, by the Worker, saved with the step's success in the same SaveChanges, trace id = the execution's correlation id); none for a failure.
    - Publish audit: `WorkflowPublished` carries `smsSends: [{ nodeId, connection, to, text }]`: the **templates** (placeholders and fixed words), never a data value. A fixed number typed into `to` is template text and is therefore recorded verbatim: authors should use a data field, not a real person's number.
14. **Where it runs.** Worker only: `ISmsSend` → `SmsSendService` (scoped) and the internal `ISmsSender` → `HttpSmsSender` (singleton) are registered by `AddVersoSmsConnections`, which only the Worker calls; the API process resolves neither (tested). The engine calls `ISmsSend`, never the sender. Same master key (`Secrets__MasterKey`). One migration, **no new package**.
15. **The designer.** The step card shows a message icon, the summary `sms: {connection}` and a "Sends a message" marker; the number field is monospaced; the message box shows a live counter **"n / 480"** (it counts the template as typed, placeholders included) and the **static** hint "Up to 160 characters is one SMS; longer messages are sent in parts.", both linked to the box with `aria-describedby`. The box has no hard length limit: a longer paste is kept, the counter turns red and an alert asks to shorten it; the server's 480 limit decides. There is **no live parts counter**: the parts depend on the filled-in text and on Unicode, which only the Worker knows. The SMS connection form gets the switch (with the confirmation above, focus on "Keep sending off", Escape cancels only the confirmation), the prefixes field and a "Sending on" badge on the card; a marketing connection with sending on shows "Not used in workflows" instead, and its card and dialog say "Marketing connections can't be used in workflows."

## Consequences

- **A real message reaches a real person and cannot be recalled.** The guards are the administrator's switch, the allowed prefixes, transactional only, the text rules and the never-repeat rules. None of them can stop a wrong but well-formed number in an allowed country, or a wrong text built from correct data.
- **Duplicates after an unknown outcome.** After a timeout, a lost connection, a 5xx or a crash the message may have been sent; a person who retries may send it twice. Check Brevo's log by the tag first (runbook C2).
- **Cost and volume: no daily or monthly cap** (owner decision 4). A For each sends one SMS per item (at most 200 items per run), and many runs send many messages. A cap would need a send-log table; recommended if volumes grow. Keep the Brevo account's credit low enough to limit the damage.
- **Personal data goes to a third party** (the number, and any name or detail in the text, to Brevo). The bank's data-protection review must cover it.
- **Any workflow editor can send through any switched-on connection**, to any number in its allowed countries. Switch sending on only for connections meant for workflows, keep their prefix list short, and review the publish audit (`smsSends`).
- **No marketing**, no consent or opt-out handling, no scheduling, no delivery reports (a 2xx says Brevo accepted the message, not that the phone received it), no replies, no other providers, no link tracking.
- **Conservative refusals:** the invisible-format rule also refuses the zero-width non-joiner (U+200C) and the Arabic number signs, which some Persian, Kurdish or Indic texts use, and the England / Scotland / Wales flag emoji (built from tag characters). A prefix of 1 digit is accepted: an administrator typing `3` allows every `+3x` country. A step whose run time limit fires just before the request is reported as an unknown outcome although nothing left.
- **A number without its leading `+` or `00` is read as international** (owner decision, not changed here). The run data's number is not interpreted in any national format: `99000000` is read as the digits `99000000`, and a national number whose first digits happen to equal an allowed prefix (for example a national number starting with `30` when `30` is allowed) passes every check and is sent to that country. Run data should therefore carry full international numbers (`+357…` or `00357…`), and administrators should keep the prefix list as narrow as the flows need.
- **Tags are shared** by two Send SMS steps of the same run and iteration (item 8).
- **With a system proxy the address guard checks the proxy, not the target** (the open question of ADR 0021 applies here too).
- **The send path** (item 9) and **Brevo's tag limits** (item 8) are unresolved until the owner's manual check.
- **Found while building, NOT fixed here (follow-ups for the owner):** (a) ~~Fetch from API turned a data number such as `1e400` into the text "Infinity"~~ fixed afterwards (2026-11-23): the shared `ApiFetchStep.ScalarText` now returns null for a number no double can hold, so Fetch from API reports `fetch.value_invalid` (nothing sent) and Send SMS keeps its own more specific `sms.value_invalid`; (b) a lone-surrogate escape in any node's configuration string makes the schema check throw before the node rules run (pre-existing, every node).
- **Not built:** Send to API (changing calls), Upload to SFTP (still simulated) and other SMS providers each need their own ADR; Deliver via API stays simulated.

## Unverified

**Nothing is verified against live Brevo.** Every test fakes HTTP (a fake handler for the sender and the service wired into the engine, a scriptable fake `ISmsSend` for the engine) and no test sends a real SMS. The **first real send is the owner's manual check**, with the owner's own number, on a non-production machine: Test connection on the SMS connection (this also settles the send path, item 9), then switch "Allow workflows to send SMS" on with the owner's country prefix only, and run the sample [send-sms-individual-or-corporate.md](../samples/send-sms-individual-or-corporate.md) with the owner's number in the individual customer's data. Not exercised by any test: a real TLS failure, Brevo's real 400 bodies, Brevo's handling of the tag.
