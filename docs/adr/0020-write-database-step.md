# ADR 0020: Write to database step (INSERT / UPDATE / DELETE typed by a workflow author)

- Status: accepted (implemented 2026-11-19, awaiting acceptance).
- Requested by the product owner on 2026-11-19 ("start Phase 2, write SQL"): a flow must be able to write values taken from an XML file to a database. Decisions of the owner on 2026-11-18 and 2026-11-19: SQL typed freely by **anyone who can edit a workflow**; a per-connection **"Allow writes" switch**, administered by administrators and **off by default**; a write is **never retried automatically**; the exception to the CLAUDE.md rule against author-written code, approved on 2026-11-18 for read and write SQL, is used here; a **separate step** from Query database; row cap defaults to 1 and goes up to 1000. This is Phase 2 of [ADR 0019](0019-query-database-step.md); the branch was started from the Phase 1 branch, which is not merged yet. Design: `docs/superpowers/specs/2026-11-18-write-database-step-design.md`.
- CLAUDE.md is amended in the same change: the safety exception and the approved-integrations list name this step and the switch.

## Context

The Database connections of ADR 0016 can be tested, and since ADR 0019 a workflow can read from them. A common next need is the other direction: after a document is made, record it (an audit row), or update a status in a bank system, with values from the run's data. Phase 1 deliberately built read only. A write is different in kind: it changes data that Verso does not own, a rollback only protects a statement that did not finish, and when the answer is lost (timeout, lost connection, Worker stopped) nobody can tell whether it happened. The substance of this ADR is therefore the switch, the guard, the row cap and the rules for never repeating a write.

## Decision

1. **The step.** `write-database` ("Write to database", category output), input `in`, ports `written` (the success exit) and `failed` (optional to connect, item 9). Settings: `connection` (key of an active Database connection; the schema marks the field `x-requires-writes`, which the designer reads), `sql` (up to 4,000 characters, one INSERT, UPDATE or DELETE), `parameters` (lines `name = data.path`, names without the `@`, the same rules and parser as Query database: case-insensitive duplicates refused, every `@name` needs a line and every line a `@name`), `maxRows` (default 1, 1 to 1000) and `timeoutSeconds` (default 15, 1 to 60). There is no result name: **the run's data is not changed**. The step result holds **`rowsAffected`, `durationMs` and `connection` (the key)**, never a value and never the SQL. The Worker clamps `maxRows` and the time again whatever it is given.
2. **The "Allow writes" switch.** Column `connections.DatabaseConnections.AllowWrites` (migration `DatabaseConnectionAllowWrites`, default false). Only administrators can change it (the whole Database connections API is administrators only); it is on the create and update requests and on the `DatabaseConnection` response as `allowWrites`. Changing it is audited as `DatabaseConnectionWritesChanged` (`{ key, allowWrites }`, also on create when switched on) and `allowWrites` is also among the changed field names of `DatabaseConnectionUpdated`. `GET /api/v1/database-connection-options` (workflow authors and administrators) gains `allowsWrites` so the designer can warn. **A write on a connection with the switch off is refused with `db.writes_not_allowed`, in the Worker, before the password is decrypted and before any connection is opened.** Publishing does not check the switch: it is read at run time, so an administrator can switch writes off after a workflow was published and the next run fails with that code. Query database ignores the switch.
3. **WriteGuard: `SqlGuard.CheckWrite`.** The same tokenizer as read mode (comments, strings and quoted names skipped; every Phase 1 dialect refusal of ADR 0019 item 2 applies unchanged), run at design time (the workflow validator and again when publishing) and again at run time inside the service before any connection is opened. It accepts exactly one statement and refuses, with `sql.not_write` unless another code is named:
   - a first word that is not INSERT, UPDATE or DELETE (the verb may appear only there); a second INSERT, UPDATE or DELETE and every other word of the Phase 1 forbidden list (MERGE, DROP, ALTER, CREATE, TRUNCATE, EXEC, COMMIT, ROLLBACK, DECLARE, SET, WAITFOR, ...) anywhere, inside parentheses too (quote a column with such a name);
   - `INTO` anywhere except directly after INSERT (`sql.select_into`; this refuses `SELECT ... INTO` and `OUTPUT ... INTO`);
   - an UPDATE needs exactly **one `SET`**, at the top level and before the WHERE; any other SET (a second one, one after the WHERE, one in parentheses, one in an INSERT or DELETE) is refused; `UPDATE STATISTICS` is refused;
   - an UPDATE or DELETE needs a `WHERE` word at the top level, outside parentheses (**`sql.no_where`**). `WHERE 1 = 1` is still a WHERE: the guard only stops a whole-table write by accident;
   - at the top level (outside parentheses), things that on SQL Server would start a **second statement without any `;`**: any SELECT in an UPDATE or DELETE (a subquery goes in parentheses); in an INSERT a SELECT only as its source (not after VALUES or DEFAULT; further SELECTs only right after UNION, INTERSECT or EXCEPT, with an optional ALL / DISTINCT); the read-only T-SQL verbs IF, PRINT, THROW, RETURN, GOTO, READTEXT, FETCH, BREAK, CONTINUE, GET, MOVE; `MINUS` (SQL Server reads it as an alias, so the query after it would run as a second statement; use EXCEPT); a `WITH` not followed by `(` (a CTE; the table hint `WITH (ROWLOCK)` is fine);
   - a top-level `(SELECT` or `(WITH` that does not stand where the grammar needs an expression or a table: it must follow an operator, a comma, a keyword such as IN, EXISTS, FROM, JOIN, WHERE, SELECT, CASE, THEN, VALUES or a listed function (COALESCE, ISNULL, CAST, CONVERT, MAX, COUNT, UPPER, ... the list is in `SqlGuard`), because after a value, an alias or a name SQL Server reads it as a new statement; `APPLY` only after CROSS or OUTER;
   - a `)` without its `(`.

   `sql.empty`, `sql.too_long` (4,000), `sql.multiple_statements` (a `;` followed by more), `sql.unterminated`, `sql.bad_parameter` and `sql.unsupported_syntax` are the Phase 1 codes, unchanged. **Be honest about what this is: the guard filters tokens, it does not parse SQL.** On SQL Server statements need no `;`, so a spelling nobody foresaw could still let a **second, read-only statement** through. It can do nothing the write statement itself could not already do: it cannot write data with a write, DDL or procedure word, because every such word is refused anywhere in the text, inside parentheses too, but like any SELECT it can still call functions (for example an EXTERNAL_ACCESS CLR function), use sequences or take locks; and it cannot satisfy the WHERE rule, because a second statement can only bring a top-level WHERE with a top-level SELECT, UPDATE, DELETE or MERGE, and all of them are refused. During review the guard was attacked on LocalDB and each hole found was closed (a trailing `SELECT ... WHERE` after the write, `MINUS` and function names used as aliases, `(SELECT` after a value, DEFAULT VALUES and OUTPUT variants); the open question is that only a real parser (Microsoft.SqlServer.TransactSql.ScriptDom, MIT, a new package that needs the owner's approval) could count statements exactly. **The guard is defence in depth. The protection is the switch and the login's own permissions.**
4. **Execution, per provider (Worker only).** One statement inside a transaction, in `DbWriteExecution` (shared, no driver referenced), a runner per provider:
   - **SQL Server** (`SqlServerWriteRunner`, in Infrastructure beside the query runner): a driver transaction (ReadCommitted), the connection string of the query runner without `ApplicationIntent=ReadOnly`, no pooling.
   - **PostgreSQL**: a plain `BEGIN` (raw statements) on a connection string built without `default_transaction_read_only`, then `COMMIT` or `ROLLBACK`.
   - **MySQL / MariaDB**: `START TRANSACTION` (never READ ONLY), then `COMMIT` or `ROLLBACK`.
   - **Oracle**: a driver transaction; the `@name` placeholders become `:p1..:pN` as in the Oracle query runner, parameters are bound by name, a trailing semicolon is dropped.

   Values are driver parameters only, as in Phase 1. The command has the step's time limit.
5. **The row cap.** The statement is committed only when `ExecuteNonQuery` reports at most `maxRows` rows changed. More: **rollback**, `db.too_many_rows_affected`, nothing changed (a known failure). A negative count (for example `SET NOCOUNT ON` set on the server) cannot be checked: **rollback**, `db.rows_affected_unknown`. **The cap counts only the rows the statement reports.** Rows changed by cascading foreign keys are not counted, nor are rows changed by a trigger that sets `NOCOUNT ON`; rows a trigger changes are counted unless it does. The cap limits mistakes, it is not a guarantee of how much data changes.
6. **Known and unknown failures.** After the statement was sent, a failure the server reported for the statement itself (syntax, permission, unknown column, constraint, duplicate key, data conversion, deadlock victim; the error numbers or SQLSTATE classes are tables in each runner) rolls the transaction back and is a **known failure**: the code is `db.query_failed` ("The database could not run the statement. Check the statement, the table and column names and the login's permissions."), nothing changed. Write failures use statement wording (`DatabaseQueryMessages.ForWrite`: also `sql.empty`, `sql.too_long`, `sql.unterminated`, `sql.select_into`, `sql.unsupported_syntax`); the Query database step keeps its Phase 1 wording. A timeout, a lost connection, a failing commit or anything unexpected **after** the statement was sent is an **unknown outcome**: the code stays the real one (`db.timeout`, `db.unreachable`, `db.query_failed`) and the message is `The outcome is unknown: the statement may or may not have changed data. Check the database before running this step again.` A failure **before** sending (cannot connect, login failed) changed nothing and uses the probes' wording. **A failing commit is always an unknown outcome.** The driver's text, the server, the login and the values are never in a message. Once the commit succeeded the result is success, whatever closing the connection throws. If a cancellation arrives (Worker shutdown), it wins even over a failing commit and the attempt is treated as possibly unknown, even when it came before the statement was sent.
7. **Never retried, never repeated.**
   - **No automatic retry, whatever the code:** every failure of the step ends the run **Failed** at once (the engine throws it as not retryable). Only a person (Operator or Admin: the Retry button or `POST /api/v1/executions/{id}/retry`) can run the step again, **and that runs the statement again by that person's decision**.
   - **The Running-step guard.** When a run finds a Write to database step still `Running` (an earlier run started it and never recorded how it ended), the engine **does not send the statement again**: it records the step Failed with the outcome-unknown message and fails the run with **`write.outcome_unknown`** (not retried). A Worker stopping while a write is in progress **leaves the step Running** (other steps are marked interrupted) so that the next run finds it. A stop that comes before the statement was sent is still reported as unknown next run: the wording is deliberately cautious.
   - **A Succeeded write is not replayed on resume** (after an automatic retry of a later step, an approval wait or a restart): unlike Query database it changed nothing in the run's data, the database is never called, and its row count stays in the step record.
   - **A For each with a write resumes only over the same list (`loop.items_changed`).** On resume the engine rebuilds the loop's list from the data and finds the items already done by their step rows **by position**; a Query database step before the loop reads again, so the list can differ (fewer rows because the writes marked some as done, new rows, or another order from a SELECT without ORDER BY). By position that would skip an item whose place already has a Succeeded write (the run would end Succeeded with that item never written) or write an item again at a later place. So when a For each's loop contains a Write to database step anywhere (behind a branch too), its step result also records `itemsFingerprint`: an HMAC-SHA256 over the item count and each item's JSON text, in order, keyed by the execution id and the step id, **one hash for the whole list and never a value**. Before any item runs, on the first pass and on every resume, the list is compared with it; on any difference of count, order or content the run fails with **`loop.items_changed`** (not retried) and nothing in the loop runs. Writes already made for earlier items stay; the message tells the operator to check the database and submit the data again if needed. A Retry of that run compares again and fails the same way unless the data is back as it was (the check is never re-baselined). A recorded For each result without a fingerprint fails the same way (cannot be verified); only a run from before this check could have one, and write steps are newer. Loops without a write step are unchanged (their result is still `{ count }`). Limits: the check sees the list, not the database, so a write in a loop over a list that is equal but means something else now is not detected; a list built from the submitted data never changes.
   - **The run's time limit (5 minutes):** if it runs out while the statement is in progress the step fails with `execution.timeout` and the unknown-outcome wording, not retryable. This branch has no automated test (no seam to shorten the limit).
   - A second Worker that takes the run after a lease expired is stopped by the row version of the execution, as for every step.
8. **Who may author, and what is recorded.** Anyone who can edit workflows may type write SQL (owner decision). **Publishing audits what will run:** `WorkflowPublished` carries `databaseWrites: [{ nodeId, connection, sql }]`, the SQL text and the connection key, **never parameter values or data paths** (the same shape as `databaseQueries`). **At run time each committed write is audited** as `DatabaseWriteExecuted` (`{ executionId, nodeId, iteration, connection, rowsAffected }`, entity `Execution`, actor the Worker, trace id the run's correlation id), saved in the same `SaveChanges` as the step's success; a failed write has no such entry (its step and execution records carry the code and message). Values and the SQL never appear in the step result, in the events, in logs or in error messages (tests capture the logs of a successful, a failing and a rejected run). As with Query database, an author can still copy data into what the run records by other steps (an Archive metadata pattern, say); the Write step itself never records them.
9. **Ports.** `failed` is taken **only for a missing, null or non-scalar parameter value** (the data's fault; the same checks and the same `query.parameter_missing` / `query.parameter_invalid` issues as Query database); the database is not called, and the run ends **Rejected** with `data.write_invalid` unless the port is connected. Inside a For each it ends the whole run Rejected even when the port is connected (as every rejecting port does in a loop), and later items do not run; a Rejected run cannot be retried, only submitted again. **Every database or SQL failure fails the run** (item 7), none takes a port.
10. **The designer and the Connections page.** The connection form has a switch "Allow workflows to change data", off by default; turning it on shows a confirmation ("Allow changes" / "Keep writes off", focus on the safe button, Escape cancels the confirmation) and a line that the login should be able to write only the tables the flows need; the dialog sends `allowWrites` only when the administrator touched it, so an open dialog cannot flip a switch another administrator changed. A connection card shows "Writes on". In the workflow designer the step's connection list marks connections `, writes off` and shows a warning under the chosen one (the connection field still keeps its key); the step card shows "Changes data" and the connection key; the SQL field's hint says INSERT / UPDATE / DELETE.
11. **Where it runs.** Worker only: the PostgreSQL, MySQL and Oracle runners are in `Verso.Databases` (ADR 0016 addendum 1), the SQL Server runner in Infrastructure; the API never connects (a test checks that it cannot resolve `IDatabaseWrite`). Same `DatabaseConnections:AllowedServers` rail (`db.server_not_allowed`), the password decrypted in memory only. **No new package.** Migration `DatabaseConnectionAllowWrites` (one column).

## Consequences

- **Anyone who can edit a workflow can change data as the login of any connection whose switch is on**, in whatever tables that login may write. Mitigations, in this order: give a write-capable login INSERT / UPDATE / DELETE on only the tables the flows need (`docs/setup.md`, section 8); create a **dedicated connection per purpose** and switch "Allow writes" on only for those; review the publish audit (the SQL text is in it). A per-table allow-list on the connection is a possible later phase and is not built.
- **A duplicate write is possible after a person retries a run whose write was in fact applied** (item 7), **or when the data is submitted again** after a Rejected run (which cannot be retried: inside a For each a `failed` port ends the whole run Rejected, item 9), after a Failed one or after `loop.items_changed`: a new run writes every item again, including those already written. The runbook says to check the target by its business key first. Write idempotent SQL where the data allows it: `INSERT ... SELECT ... WHERE NOT EXISTS (...)`, or a unique natural key (a duplicate then fails as a known `db.query_failed`), or an UPDATE that sets a value instead of adding to it. `docs/samples/write-database-audit-row.md` shows the first form.
- **The guard is conservative and refuses some harmless SQL** (rewrite it or quote the name): MySQL `ON DUPLICATE KEY UPDATE` (a second UPDATE and a second SET), MySQL `INSERT IGNORE INTO` and `REPLACE INTO`, SQL Server `INSERT TOP (n) INTO` (INTO must be the word right after INSERT), PostgreSQL `ON CONFLICT ... DO UPDATE SET` (a SET after the verb), `MERGE`, Oracle `INSERT ALL`, `OUTPUT ... INTO`, a subquery as the first thing after `ORDER BY` or `OUTPUT` (`ORDER BY COALESCE((SELECT ...), a)`; BY and OUTPUT are not in the list of words an expression may follow), writing through a CTE (`WITH ... INSERT`), a subquery as the first argument of a function the guard does not list (use `CAST((SELECT ...) AS type)`, or move it after another argument), Oracle `MINUS`, top-level MySQL `IF()`, top-level `OFFSET` / `FETCH`, `INSERT INTO t (cols) (SELECT ...)` (write `INSERT INTO t (cols) SELECT ...`), and columns or aliases named like a refused word unless quoted. `RETURNING` is allowed. Every Phase 1 limitation of the tokenizer still applies (no backslash, `#`, `--` without a space, `$`, non-ASCII outside quotes, ...).
- **MySQL / MariaDB: InnoDB is assumed.** On MyISAM or MEMORY tables a failed multi-row statement can leave earlier rows changed while the step reports a known failure; with a non-strict `sql_mode` the data errors (1264, 1265, 1366) are warnings, not errors, so the row is written truncated. MySQL error 1205 (lock wait timeout) is classed as an unknown outcome, because MySqlConnector reports its own command timeout with the same number. PostgreSQL 25006 (read-only transaction) is classed known.
- **Rollback relies on non-pooled connections** in the unusual case that a raw `ROLLBACK` itself fails: closing the connection then discards the transaction. Pooling is off in every runner's connection string; turning it on would break that assumption.
- **The data root is not changed** and there is no result: a later step cannot see the number of rows except in the step's recorded result.
- **Inside a For each the write runs once per item** (it is an ordinary step): the row cap applies per statement, not per run, and there is one `DatabaseWriteExecuted` entry per item. The first item that fails or is rejected ends the whole run; items before it keep their writes (item 7, `loop.items_changed` for a list that changed before a resume).
- **The commit has no time limit of its own**: the step's time limit applies to the statement; a commit that hangs waits on the driver (and on the run's 5-minute limit, which then reports the outcome as unknown).
- Parameter problems of a write carry the Query database codes `query.parameter_missing` / `query.parameter_invalid` (item 9): one parser and one set of checks for both steps.
- Phase 1 limitations that still apply: Parallel branches do not combine their data (ADR 0019 item 10); queried values are the author's to expose; one statement only; no stored procedures; no schema browser.
- **Still not built, each needs its own ADR:** Phase 3, an API call step (using the API connections of ADR 0017); Phase 4, a Send SMS step (using the SMS connections of ADR 0018); Phase 5, an SFTP step. Until then Deliver via API and Upload to SFTP stay simulated and no workflow step sends an SMS.

## Unverified

**Only SQL Server ran against a live server** (LocalDB in the test suite: commit, rollback, the row cap, the timeout after send, the refusal before the password is decrypted, no connection opened for refused SQL, and the guard's attack texts). **The PostgreSQL, MySQL / MariaDB and Oracle runners are verified only structurally** (the shared executor over a fake connection, error mapping from tables, connection strings, parameter building). Open risks, to try on a non-production server of each type before relying on it:

- Raw `BEGIN` / `COMMIT` / `ROLLBACK` statements on Npgsql and MySqlConnector (that the driver does not wrap or reject them, and that the statement runs inside the transaction).
- Oracle: the driver transaction, `BindByName` with the synthetic names, and the row count that `ExecuteNonQuery` reports for INSERT ... SELECT.
- How each driver behaves when the command is cancelled or times out mid-statement (the executor assumes the rollback that follows works, or that closing the connection discards the work).
- Parameter binding on PostgreSQL and MySQL: the fake connection of the tests does not accept parameters, so `@name` binding on Npgsql and MySqlConnector is unexercised.
- The real exception types and properties behind the error tables (`PostgresException.SqlState`, `MySqlException.Number`, `OracleException.Number`): the tables come from the vendors' documentation, not from tries. A wrongly classed code is classed unknown (safe) or known (unsafe: a retry could duplicate); the known lists were kept to errors that reject the statement.
- That the guard's claims about PostgreSQL, MySQL and Oracle tokenizing come from their documentation.
- No test reaches the run's 5-minute time-limit branch (item 7), and no test runs the whole engine against a live database other than through a fake service plus the service's own LocalDB tests.
