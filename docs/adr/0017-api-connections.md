# ADR 0017: API connections managed in the app (HTTP, test only)

- Status: accepted (implemented 2026-11-17, awaiting acceptance).
- Requested by the product owner on 2026-11-17: "implement the API in connection ... some APIs need keys so need to connect any API like we do for DBs", with `https://api.frankfurter.dev/v1/latest?base=EUR&symbols=USD,GBP` as the example. As with database connections (ADR 0016), the scope is **a real connection with Test connection only**. The **Deliver via API** step stays simulated (CLAUDE.md: "no HTTP calls") and no step uses an API connection yet.
- CLAUDE.md listed API calls among the integrations that stay simulated until approved; this ADR records the approval, scoped to one GET from the Worker per test.

## Context

The Connections tab can already hold real email relays (ADR 0015) and real database connections (ADR 0016), with encrypted write-only secrets and a Test connection run by the Worker. Web APIs are the next kind: some need no key (Frankfurter), others an API key in a header or in the address, a bearer token, a login, or OAuth.

## Decision

1. **One flow.** In Connections, **New connection** with the authentication **HTTP API** switches the dialog to the API form (base address, test request path, how the API is secured, secret, timeout, key) and creates a real connection. Real connections appear as cards in *Data sources* with a switch, **Configure** and **Test connection**. Only administrators see or create them. Pasting a full address with a query (the Frankfurter example) is split into the base address and the test path.
2. **Storage.** `connections.ApiConnections` (migration `ApiConnections`): key (unique), name, base address, test path, credential kind, name (header, parameter, user or client id), token address and scope (OAuth), timeout, active, and the encrypted secret. Deactivated, never deleted (grants deny DELETE).
3. **Credential kinds:** none; API key in a **header** (name chosen); API key in the **query** (parameter name chosen; the key is URL-encoded; the form warns that some servers log addresses); **Bearer** token; **Basic** (user name and password); **OAuth 2.0 client credentials** (the client id and secret go as HTTP Basic to the token endpoint, the access token is used once and never stored). Not done: other OAuth flows, mutual TLS, request signing, custom headers.
4. **The secret is write-only and encrypted**, exactly as in ADR 0015 and 0016: AES-256-GCM with the master key `Secrets:MasterKey` kept outside the database, context `api-connection:{key}`. Never returned, logged, audited, exported or shown; responses carry only `hasSecret`. Choosing "no authentication" drops a saved secret.
5. **Test connection runs on the Worker**: `POST /api/v1/api-connections/{id}/tests` records a row in `connections.ApiConnectionTests` (audited as `ApiConnectionTestRequested`) and queues a Hangfire job. The Worker decrypts the secret in memory and sends **one GET** (for OAuth, one token request first) with `HttpClient`: **no new package**. Success is any 2xx answer.
6. **What a test keeps:** the HTTP status, the time in milliseconds, the content type and the size in bytes. **The response body, the headers, the address and the secret are never stored or shown** (the body is read only to count its size, at most 1 MB). Results use Verso's own codes and wording: `api.unauthorized` (401, 403), `api.not_found`, `api.rate_limited`, `api.redirect_not_followed`, `api.client_error`, `api.server_error`, `api.timeout`, `api.unreachable`, `api.certificate_untrusted`, `api.blocked_address`, `api.host_not_allowed`, `api.token_failed`, `api.secret_unreadable`, `api.connection_unavailable`, `api.test_failed`.
7. **Server-side request forgery.** An administrator chooses what the Worker calls, so: **https only** (no credentials in the address, no query on the base, the test path starts with a single `/` and can't become another host); **redirects are never followed**; the Worker connects only to addresses that are **not loopback, link-local (including the cloud metadata address 169.254.169.254), unspecified or multicast**, checked when connecting (so a name that later resolves to one is refused too: `api.blocked_address`); TLS 1.2 or 1.3 with the Worker's certificate store; the configured timeout (1 to 120 s). Internal (private-range) addresses are allowed because the bank's own APIs live there; the optional **`ApiConnections:AllowedHosts`** (Worker configuration) limits the hosts (the API host and, for OAuth, the token host); anything else fails with `api.host_not_allowed` without a request. **Recommended in production.**
8. **Who and audit.** Administrators only. Audited with changed field names, never values: `ApiConnectionCreated`, `ApiConnectionUpdated`, `ApiConnectionSecretChanged`, `ApiConnectionDeactivated`, `ApiConnectionActivated`, `ApiConnectionTestRequested`. Test rows are deleted after 24 hours (hourly Hangfire job).
9. **Least privilege.** The API may select, insert and update in the `connections` schema; the Worker may select, and update or delete only test rows; nobody may delete a connection; only the API inserts tests.

## Consequences

- **Another credential type is stored by Verso** (encrypted), under the same master key. Losing the key loses all stored secrets (email, database and API).
- **The Worker makes real outbound HTTPS calls** to hosts an administrator names. Use read-only or test credentials, set `ApiConnections:AllowedHosts` in production, and make sure the Worker server's egress (firewall, proxy) allows the host. The default system proxy is used when configured.
- The query-string kind puts the key in the address, which the remote server, proxies and its logs may record; prefer a header where the API allows.
- A test proves the address and credentials work for **one GET**. It says nothing about other paths or methods.
- Using a connection in a workflow step (the Deliver via API step, a data lookup) needs its own ADR (which requests, payload handling, retries, personal data) and stays simulated until then.
