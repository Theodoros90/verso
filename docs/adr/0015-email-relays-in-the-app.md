# ADR 0015: Email relays managed in the app, with the SMTP password stored encrypted

- Status: accepted (implemented 2026-11-16, awaiting acceptance). Chosen by the product owner ("Stored encrypted on the server").
- Builds on ADR 0006 (Send email) and its addendum 1 (named relays in configuration). Changes one rule: ADR 0006 said the password comes only from the environment or a secret store and "never from a workflow". It still never comes from a workflow. It may now also be typed once in the Configuration drawer and is then stored encrypted by Verso.

## Context

An administrator wants to add an SMTP relay (Gmail, Outlook 365, a bank relay) and its password in the Configuration drawer, not by editing the Worker's configuration and environment on the server. The Connections tab is frontend-only and simulated, and the Worker can't read the browser, so a real setup needs the relay and its password stored on the server.

## Decision

1. **A new table of relays.** `Mail.EmailRelays` (module folder `Mail`, own SQL schema): `Key` (unique; the same key pattern as ADR 0006 addendum 1), `Name`, `Host`, `Port`, `EnableSsl`, `UserName`, `FromAddress`, `FromName`, `TimeoutSeconds`, `AllowedRecipientDomains`, `IsActive`, `PasswordProtected` (nullable), timestamps and who changed it. Relays are never deleted, only deactivated (as categories are).
2. **The password is write-only.** The API accepts it on create or update and never returns it: responses carry only `hasPassword`. An update that leaves the password out keeps the stored one. Clearing it is an explicit action. It is never written to the audit trail, logs, history, an export or the OpenAPI examples.
3. **Encrypted at rest with AES-256-GCM** (`System.Security.Cryptography`, no new package). The 32-byte master key is **not in the database**: the administrator sets it as the environment variable `Secrets__MasterKey` (base64) or in the bank's secret store, on the API and on every Worker. Each password gets a fresh random nonce; the stored value holds version, nonce, tag and ciphertext. Without a master key the API refuses to save a password (`secrets.not_configured`) and the Worker can't decrypt one. The key id is stored so the key can be rotated later (not built now).
4. **Who may do it.** Only the administrator role (the same policy that manages document categories and configuration packages). Every create, update, deactivate and password change is audited (`EmailRelayCreated`, `EmailRelayUpdated`, `EmailRelayDeactivated`, `EmailRelayPasswordChanged`) with the key and the changed field names, never a value.
5. **Resolution in the Worker.** `IEmailRelayStore` (Application) finds a relay by key. The Infrastructure implementation looks in the database first (active relays) and falls back to the `Email` configuration of ADR 0006 (top-level = `default`, `Email:Relays:{key}`). A relay in the database with the same key as one in configuration wins. Existing configuration-only installs keep working unchanged. `SmtpEmailSender` does the rest as before (ADR 0006 decisions 5 to 8).
6. **Frontend (one flow).** There is no separate screen or button for email relays. In the Connections tab, **New connection** with the authentication **SMTP credentials** switches the dialog to the email form (presets Gmail / Outlook 365 / iCloud, server, port, security TLS or none, timeout, username, **password** (write-only), sender, relay key, allowed recipient domains) and creates a real relay through the API. Real relays appear as cards in *Delivery channels*, with a switch (activate / deactivate) and **Configure** (the same form; the key is fixed, an empty password keeps the saved one, a box removes it). Only administrators see them or can create one. Every other connection stays simulated. The old simulated "SMTP relay" card and its browser-only form were removed.
7. **Test connection (built).** The API never sends mail (ADR 0006), so "Test connection" follows the folder-input "Test access" pattern: `POST /api/v1/email-relays/{id}/tests { toAddress }` records a row in `mail.EmailRelayTests` (audited as `EmailRelayTestRequested`, without the address) and queues a Hangfire job; the Worker sends one fixed message ("Verso test email") through the **saved** relay and records `Succeeded` or `Failed` with the usual error code (`email.relay_unavailable`, `email.recipient_refused`, `email.password_unreadable`...). The recipient is kept only until the test ends (then cleared), rows are deleted after 24 hours (hourly Hangfire job), and the result never contains an address. A switched-off relay can't be tested (409 `email_relay.inactive`). The Configure dialog has the button; a new connection says to create it first. Not in this ADR: bounce handling, OAuth (Gmail and Outlook may require app passwords or OAuth; plain `SmtpClient` supports neither OAuth nor some modern auth modes, see ADR 0006 decision 2).

## Consequences

- **A credential is now stored by Verso** (encrypted, but still a credential). The bank must accept this and protect the master key. The previous rule "Verso never stores credentials" stays true for folder input and every other integration.
- The master key is the single point to protect and back up. Losing it makes stored passwords unreadable; they must be typed again.
- API and Worker need the same master key. A Worker without it can only use relays without a stored password or with the environment-variable password.
- New migration `EmailRelays`; API contract changes (OpenAPI snapshot and generated types).
- Gmail and Microsoft 365 increasingly refuse basic passwords: a Gmail app password works today; Microsoft 365 often needs OAuth, which is not supported (ADR 0006).
- Not done: key rotation, per-relay rate limits, OAuth, reading the master key from a hardware module.
- **Open points:** the test sends a real message, so use a synthetic recipient; the grants in `tools/db/least-privilege.sql` give the API write access to the `mail` schema and the Worker read access (plus update and delete on `mail.EmailRelayTests`), and nothing may delete a relay.

## Addendum 1 (2026-11-16): the Send email step picks a connection from a list

- The step's optional setting is now titled **Email connection** and is a **dropdown** of the global email connections instead of a typed key: "Default email connection" (empty, the Worker's default relay), then each connection as "Name (key)", switched-off ones marked. The workflow still stores the key only. A saved key that is no longer in the list stays selectable and is marked "(not found)" so an old workflow never changes silently; the run still fails with `email.relay_unknown` if the connection is missing or off.
- `GET /api/v1/email-relay-options` feeds the dropdown. It returns `{ key, name, isActive }` only (no server, sender or account) and any signed-in role may read it, because workflow authors are not administrators. The administrators-only list stays at `/api/v1/email-relays`.
- The node schema still validates the key with the same pattern; the widget is `x-widget: "email-relay"` and is not an enum (the list is dynamic).
