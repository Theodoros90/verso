# ADR 0018: SMS connections managed in the app (Brevo, Test connection sends one real SMS)

- Status: accepted (implemented 2026-11-17, awaiting acceptance).
- Requested by the product owner on 2026-11-17: "Add a connection for SMS" using Brevo's settings (base address, API key, sender, type, Unicode, organisation prefix). When asked whether this should be only the connection or also a Send SMS step, the answer was "real SMS", then "Just add to Connection, then I will use it in the flow; you can test the SMS" with a number given for the test. So the scope is **a real connection whose Test connection sends one real SMS**. A **Send SMS workflow step is not part of this ADR** and no step uses an SMS connection yet.
- CLAUDE.md listed SMS (and every message sent to a person) among the integrations that stay simulated until approved; this ADR records the approval, scoped to one SMS per test, to a number typed by an administrator.

## Context

The Connections tab can already hold real email relays (ADR 0015), database connections (ADR 0016) and HTTP API connections (ADR 0017), each with an encrypted write-only secret and a Test connection run by the Worker. SMS is the next delivery channel. Brevo (an SMS provider) exposes `POST /v3/transactionalSMS/sms`, authenticated by an `api-key` header, with the fields `sender`, `recipient`, `content`, `type` (`marketing` or `transactional`), `unicodeEnabled` and `organisationPrefix`.

## Decision

1. **One flow.** In Connections, **New connection** with the authentication **SMS (Brevo)** switches the dialog to the SMS form (sender, type, Unicode, organisation prefix, base address, timeout, API key, description, key) and creates a real connection. Real connections appear as cards in *Delivery channels* with a switch, **Configure** and **Test connection**. Only administrators see or create them.
2. **Storage.** `connections.SmsConnections` (migration `SmsConnections`): key (unique), name, provider (`brevo`, the only one), base address (https, default `https://api.brevo.com/v3`), sender, type, Unicode, organisation prefix, timeout, description, active, and the encrypted API key. Deactivated, never deleted (grants deny DELETE).
3. **Sender rules:** up to 11 letters and digits, or up to 15 digits (a number); nothing else. Type is `transactional` (default) or `marketing`. Marketing SMS needs the recipient's consent and opt-out wording in many countries; that is the sender's responsibility, and the form says so.
4. **The API key is write-only and encrypted**, exactly as in ADR 0015 to 0017: AES-256-GCM with the master key `Secrets:MasterKey` kept outside the database, context `sms-connection:{key}`. Never returned, logged, audited, exported or shown; responses carry only `hasSecret`. It is required on create; on update, empty keeps the saved one. There is no "remove the key" (a connection without a key can't send): switch the connection off instead.
5. **Test connection sends ONE real SMS from the Worker.** `POST /api/v1/sms-connections/{id}/tests` takes `{ "recipient": "+357 99 000000" }` (international format: optional `+` or `00`, then 8 to 15 digits starting 1 to 9; spaces, dots, dashes and brackets are ignored; sent to Brevo as digits only). The API validates the number, records a row in `connections.SmsConnectionTests` (audited as `SmsConnectionTestRequested`, **without the number**) and queues a Hangfire job. The Worker decrypts the key in memory and sends one `POST {base}/transactionalSMS/sms` with the fixed text `Verso test message` (no data in it) with `HttpClient`: **no new package**. Success is any 2xx answer.
6. **The test number.** The Worker needs the number but the database must not keep it: the API stores it **encrypted** (same master key, context `sms-test:{testId}`) in the test row, and the Worker **removes it as soon as the test has run** (success or failure). It is never audited, logged, returned or shown. Test rows are deleted after 24 hours (hourly Hangfire job).
7. **What a test keeps:** the HTTP status, the time in milliseconds, Brevo's message id, the number of SMS parts and the credits left. **The number, the text, Brevo's answer and the key are never stored or shown.** The answer is read (at most 64 KB) only to extract those values and, on a 400, to tell a bad number or an empty balance from other mistakes. Verso's own codes and wording: `sms.unauthorized` (401, 403), `sms.invalid_recipient`, `sms.insufficient_credits`, `sms.rate_limited`, `sms.redirect_not_followed`, `sms.client_error`, `sms.server_error`, `sms.timeout`, `sms.unreachable`, `sms.certificate_untrusted`, `sms.blocked_address`, `sms.host_not_allowed`, `sms.secret_unreadable`, `sms.recipient_unreadable`, `sms.connection_unavailable`, `sms.test_failed`.
8. **Each test costs a credit and rings a real phone, so:** the job is **never retried** and a duplicate delivery does nothing (only a test still `Queued` is run, so at most one message per test), and the API refuses a second test for the same connection within **30 seconds** (409 `sms_connection.test_too_soon`). A timeout may mean the message was or was not sent; the message says so.
9. **Server-side request forgery.** Same rules as ADR 0017: **https only** (no credentials in the address, no query on the base); **redirects are never followed**; the Worker connects only to addresses that are **not loopback, link-local (including 169.254.169.254), unspecified or multicast**, checked when connecting (`sms.blocked_address`); TLS 1.2 or 1.3; the configured timeout (1 to 120 s). The optional **`SmsConnections:AllowedHosts`** (Worker configuration) limits the hosts; anything else fails with `sms.host_not_allowed` without a request. **Recommended in production** (for example `api.brevo.com`).
10. **Who and audit.** Administrators only. Audited with changed field names, never values: `SmsConnectionCreated`, `SmsConnectionUpdated`, `SmsConnectionSecretChanged`, `SmsConnectionDeactivated`, `SmsConnectionActivated`, `SmsConnectionTestRequested`.
11. **Least privilege.** The API may select, insert and update in the `connections` schema; the Worker may select, and update or delete only test rows; nobody may delete a connection; only the API inserts tests.
12. **Layering.** `ISmsProbe` (Application) is implemented by `BrevoSmsProbe` in Infrastructure and registered in the Worker only (`AddVersoSmsConnections`); it reuses the connection handler and address guard of the HTTP API probe. The API never calls Brevo.

## Consequences

- **Another credential is stored by Verso** (encrypted), under the same master key. Losing the key loses all stored secrets (email, database, API and SMS).
- **The Worker makes real outbound HTTPS calls and sends real SMS** to hosts an administrator names, to numbers an administrator types. Use Brevo credentials limited to what is needed, set `SmsConnections:AllowedHosts` in production, and make sure the Worker server's egress allows the host.
- **A key that was pasted into a chat, ticket or file must be treated as exposed**; rotate it in Brevo and type the new one in Configure.
- Brevo accepting the message (HTTP 201) says nothing about delivery to the handset; delivery receipts are not tracked.
- Using an SMS connection in a workflow (a **Send SMS** step: recipient from data, message text, retries, at-least-once delivery, personal data in history, consent for marketing) needs its own ADR and stays unbuilt until then.
- Not done: other providers, sending anything but the fixed test text, scheduling, delivery reports, unsubscribe handling, per-country limits.
