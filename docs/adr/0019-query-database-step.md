# ADR 0019: Query database step (read-only SQL typed by a workflow author)

- Status: accepted (implemented 2026-11-18, awaiting acceptance).
- Requested by the product owner on 2026-11-18: a workflow should be able to "call any DB ... in parallel with XML, then generate a document". The owner chose **SQL typed freely by workflow authors**, **read-only first**, and decided that **anyone who can edit a workflow may author the SQL** (no separate administrator role for it). The owner explicitly approved the **exception to the CLAUDE.md rule against author-written code**, for read SQL (this ADR, built now) **and for write SQL (Phase 2, not built)**. Design: `docs/superpowers/specs/2026-11-18-query-database-step-design.md`.
- CLAUDE.md is amended in the same change: the safety rule keeps its exception for this step only, and the approved-integrations list names it.

## Context

The Connections tab holds real database connections (ADR 0016: SQL Server, PostgreSQL, MySQL / MariaDB, Oracle) whose password is encrypted (master key `Secrets:MasterKey`) and which only run `SELECT 1` in Test connection. No workflow step used them. A common need is to take an identifier from the incoming data (an account number from an XML file), read a few fields from a bank system, merge them and generate a document. Approach B of the design was chosen: the author types the SQL in the step. It is the smallest build and the most flexible, and it is the one that runs author-written text against a database, so the guards below are the substance of this ADR.

## Decision

1. **The step.** `query-database` ("Query database"), an ordinary step with input `in` and ports `found`, `not-found` (optional to connect) and `failed` (item 8 says when it is taken). Settings: `connection` (key of an active Database connection, picked from a dropdown that shows its name and database type), `sql` (up to 4,000 characters), `parameters` (lines `name = data.path`, names without the `@`; two lines whose names differ only in case are refused as duplicates, because SQL Server would declare the variable twice), `resultName` (where the result goes; `iteration` is reserved), `maxRows` (default 1, 1 to 100) and `timeoutSeconds` (default 15, 1 to 60). The result is **merged into the run data** at `resultName`: the rest of the data is kept, but **a top-level field that already has that name is replaced**. **One row becomes an object, several an array**; zero rows change nothing (port `not-found`). Limits: rows 1..100, time 1..60 s, and a **256 KB** cap on the serialised result. Over the cap, the rows read so far are kept and marked truncated; when not even one row fits, the step fails with `db.result_too_large`. Duplicate or empty column names fail with `db.bad_column` (a row would lose data). The field and column names used in samples and tests are synthetic.
2. **SqlGuard (a safety net, not the protection).** A tokenizer, not a regular expression, reads the SQL (strings, quoted names and comments are skipped, so a keyword inside a string is fine). It accepts **exactly one `SELECT` or `WITH ... SELECT` statement**.
   - **Refused as a bare word anywhere:** write and DDL keywords (INSERT, UPDATE, DELETE, MERGE, DROP, CREATE, ALTER, TRUNCATE, GRANT, REVOKE, DENY), `INTO`, `EXEC` / `EXECUTE` / `CALL`, and the **statement verbs that SQL Server runs without a `;`** or that change the transaction, session or server: COMMIT, ROLLBACK, SAVE, BEGIN, WAITFOR, KILL, SHUTDOWN, BACKUP, RESTORE, DBCC, RECONFIGURE, RECEIVE, SEND, CONVERSATION, WRITETEXT, UPDATETEXT, DECLARE, USE, SET, SETUSER, REVERT, CHECKPOINT, DISABLE, ENABLE, BULK, OPEN, CLOSE, DEALLOCATE, WHILE, RAISERROR, ADD, OPENROWSET, OPENDATASOURCE, OPENQUERY, and the other databases' LOCK, VACUUM, ANALYZE, REINDEX, CLUSTER, COPY, HANDLER, PREPARE, DO, SAVEPOINT, FLUSH, PURGE, LISTEN, NOTIFY, UNLISTEN, DISCARD, RESET, REFRESH (the list is `SqlGuard.ForbiddenWords`). Not listed on purpose: verbs that cannot change anything (IF, RETURN, PRINT, THROW, FETCH, GOTO, ...) and START / LOAD / RELEASE, which can only start a statement after a `;` on PostgreSQL and MySQL and are common words (Oracle `START WITH`). A `;` followed by more than whitespace or comments is a second statement.
   - **Wherever the four databases tokenize differently, the text is refused** (`sql.unsupported_syntax`), because a quote that one database reads inside a comment and another reads as a string can hide a second statement from the guard. The final review found such a bypass in the first version: `SELECT 1 --'`, a new line, then `COMMIT DELETE FROM t --'` passed the guard, and on SQL Server with a login allowed to write it deleted the rows (a LocalDB test shows it). Refused for that reason: `--` not followed by a space, tab or line end (SQL Server, PostgreSQL and Oracle always start a comment there, MySQL does not); `#` outside text (a MySQL comment); `/*!` and `/*M!` (MySQL and MariaDB executable comments); a `/*` inside a block comment (PostgreSQL and SQL Server nest comments, MySQL and Oracle do not); a carriage return not followed by a line feed; control characters, the null character included; any non-ASCII character outside text values, double-quoted names and comments, and inside them anything but letters, marks and digits that do not normalise to ASCII punctuation (no special spaces, invisible characters, typographic or full-width quotes, yen or won sign); a backslash anywhere (MySQL escapes with it); `$` except inside a name (PostgreSQL dollar quoting and `$1`); prefixed literals other than `N'`, `B'`, `X'`, `E'` (so Oracle `q'[...]'` and `nq'`, PostgreSQL `U&'...'`, MySQL `_utf8'...'`); `[name]` and `` `name` `` holding anything but letters, digits, spaces and `_ . , +`, or with a doubled closer (PostgreSQL reads brackets as a subscript and backticks as an operator); a number glued to a name (`1DELETE` is `1` then `DELETE` on SQL Server); `@` right after a name (`t@dblink`); `:name` (Oracle and Npgsql binds, which could collide with the synthetic `:p1..`; a PostgreSQL `::cast` is fine); `{` and `}` (ODBC escapes).
   - PostgreSQL operators starting with `@` (`@>`, `@`) and `<@` give `sql.bad_parameter`; `#>` is refused with `#`. **`FOR SHARE` is not refused**; only `FOR UPDATE` (through UPDATE) and MySQL `LOCK IN SHARE MODE` (through LOCK) are. The share locks last only until the rollback.
   - Codes: `sql.empty`, `sql.too_long`, `sql.multiple_statements`, `sql.not_select`, `sql.select_into`, `sql.unterminated`, `sql.bad_parameter` (a malformed `@name`), `sql.unsupported_syntax`. The same check runs at design time (the workflow validator, and again when publishing) and **again at run time** inside the service, before any connection is opened, so a hand-edited draft or an old version cannot skip it. Tests hold a table of hostile texts per dialect. LocalDB tests prove that the service refuses the SQL Server attacks with a login that may write, opens no connection, and changes no row.
3. **Values are parameters only.** The SQL uses `@name` placeholders; each name is mapped to a data path (`parameters`) and **bound as a driver parameter**, never concatenated. A placeholder without a mapping is a design error. At run time, a path that is missing or null, or that holds an object or a list, **rejects the run** with `data.query_invalid` (the data is wrong: Rejected, not retryable). An empty text is a value and is bound. Oracle uses `:name` binds, so the Worker **rewrites the placeholders to synthetic `:p1..:pN`** (by first use), which avoids Oracle's 30-character limit, reserved words and case rules.
4. **Execution guards.** Each provider runner opens the connection and runs the statement inside a transaction that is **always rolled back**. The transaction is read-only only where the database has one: **PostgreSQL** `BEGIN READ ONLY` on a session opened with `default_transaction_read_only=on`; **MySQL / MariaDB** `START TRANSACTION READ ONLY`; **Oracle** `SET TRANSACTION READ ONLY` as the first statement of a driver transaction. **SQL Server has no read-only transaction**: it gets an ordinary transaction that is rolled back, and `ApplicationIntent=ReadOnly` does not stop a write on a plain instance (it only matters for Availability Group read-only routing, where it can also mean a lagging secondary answers). The command has a timeout. The reader stops at the row cap and, **when rows are left unread, the command is cancelled before the reader is closed**: closing alone would stream and discard the rest of the result. A LocalDB test shows 60 million rows with `maxRows` 1 coming back in under 5 seconds. Large single values are read in bounded chunks, so memory stays bounded before the 256 KB cap. **Be honest about what this is:** a rollback does not undo every side effect (sequence values, calls through a linked server or database link, functions with their own autonomous transactions), and the guard only refuses what it recognises. Therefore **the connection's database login MUST itself be read-only (SELECT only, on the tables the workflows need). That login is the protection; SqlGuard and the rolled-back transaction are defence in depth.** `docs/setup.md` says how to create one per provider.
5. **Where it runs.** In the **Worker only** (`Verso.Databases`, plus the SQL Server runner next to the existing probe). The API never connects and does not reference `Verso.Databases` or a driver (a test checks it). The step uses the same rails as Test connection: the connection's `DatabaseConnections:AllowedServers` (a server not on the list fails with `db.server_not_allowed` before any connection), and the password is decrypted **in memory** only. No new package, no migration.
6. **Who sees what.** `GET /api/v1/database-connection-options` returns `{ key, name, provider }` of every active connection to **workflow authors and administrators** (the rest of the Database connections API stays administrators only); no server, login, database or port. **Publishing audits what will run:** `WorkflowPublished` carries `databaseQueries: [{ nodeId, connection, sql }]`, the SQL text and the connection key, **never parameter values or data paths**. The same is recorded for folder paths (ADR 0001). Column values and parameter values are never logged or audited (a test captures the logs of a found, a failing and a rejected run).
7. **What the step records.** The step **Result holds only `rows` (the count), `columns`, `truncated`, `durationMs` and `connection` (the key)**, never the rows or the SQL, because the API returns step results to every reader of an execution. Rows live in the run's data (as any other step output) like the data they merge with. **The author can still expose queried values on purpose:** whatever copies data into what the run records, for example an Archive metadata pattern such as `{{db.name}}` or a file name pattern, puts the value into the archive record and into the execution's documents in the API, like any other data field.
8. **Failures and ports.** The `failed` port is taken **only for a missing, null or non-scalar parameter** (the data's fault); the run then ends **Rejected** (`data.query_invalid`) unless the port is connected. **No database or SQL failure takes a port:** it ends the step with an error. A **retryable** code (`db.timeout`, `db.unreachable`, a transient `db.query_failed`) follows the normal retry policy. A **non-retryable** `db.*` or `sql.*` code (bad SQL, permission denied, unknown column, login failed, server not allowed, result too large) ends the run **Failed** without retry, because retrying cannot fix it; an operator retries after the fix. `db.query_failed` is non-retryable for deterministic failures (a statement that returns no columns, syntax and permission error numbers) and retryable otherwise. An **unexpected exception** (not a driver error) is a final `db.query_failed` in both the service and the engine, and its text is never kept. A driver `TimeoutException` is a retryable `db.timeout` on every provider.
9. **Resume re-runs the SELECT.** Rows are not stored (item 7), so when a run resumes after an Approval wait or a Worker restart, the engine **runs the query again** to restore the data. The data **may differ** from the first run (a row changed or was added, so an object can become an array or a result can vanish). If the re-query fails, the run ends **Failed** and an operator retries it; it is not retried automatically, even for a retryable code.
10. **Parallel branches.** The step is an ordinary step and may sit on a path of Parallel branches (ADR 0009), but **the two branches' data do not combine**: after Wait for branches the run continues with the data as Branch B left it, and Merge data only joins a lookup table typed into that step, not the other branch. So "a query next to an XML parse, then merge" does **not** work. Put the steps in sequence instead (Parse, then Query database, then Generate PDF), as in `docs/samples/query-database-xml-customer.md`.
11. **Verification.** **Only SQL Server was run against a live server**: LocalDB in the test suite, including the attack texts with a write-capable login, the row-cap cancel and the timeout. The **PostgreSQL, MySQL / MariaDB and Oracle runners are verified only structurally** (the shared helper, parameter building, error mapping, the cancel over a fake connection), because no live servers exist yet. **Unverified risks:**
    - Whether ODP.NET's `BeginTransaction(ReadCommitted)` sends a statement before `SET TRANSACTION READ ONLY`. If it does, Oracle answers ORA-01453 and every Oracle query fails.
    - Oracle `LONG` / `LOB` fetch sizes (characters or bytes) and `NUMBER` values beyond .NET decimal.
    - Whether `Cancel()` stops the stream promptly on Npgsql and on MySqlConnector. MySqlConnector opens a second connection for `KILL QUERY`, and the login must be allowed to kill its own query.
    - The tokenizer's claims about PostgreSQL, MySQL / MariaDB and Oracle, which come from their documentation and were not tried.
    - No test runs the whole engine against LocalDB: the engine tests use a fake query service.

    Try each database type against a non-production server before relying on it.

## Consequences

- **Anyone who can edit a workflow can run a SELECT as the connection's login** on the connection's database, subject to publishing (audited with the SQL text). They can read whatever that login can read. Keep the login read-only and narrow, one connection per purpose, and review the audit trail. This is the price of Approach B.
- **The guard is conservative and refuses some harmless SQL.** Refused although harmless:
  - `FOR UPDATE` and MySQL `LOCK IN SHARE MODE`.
  - An unquoted name equal to a refused word, such as a column called `update`, `open`, `close`, `set`, `copy` or `reset` (quote it).
  - MySQL's `INSERT()` function and `CHARACTER SET` in a cast.
  - A backslash anywhere (use a parameter).
  - `#`: MySQL comments, SQL Server temporary tables, Oracle names with `#`.
  - `--` without a space: `5--1` (write `5 - -1`).
  - `$1` placeholders.
  - Non-ASCII names outside double quotes, and brackets or backticks holding other characters (use double quotes).
  - PostgreSQL array slices with `:`, and operators starting with `@` or `#`.
  - `table@dblink` and Oracle `q'...'` literals.

  Rewrite the query to avoid these.
- **Oracle:** a user-written `:p1` can no longer collide with the synthetic names, because `:name` is refused.
- **An empty string is a value.** A parameter whose path holds `""` is bound as an empty string; the message for a missing value says "missing or null".
- **Resume limits** (item 9):
  - A restore failure with a retryable code is not retried automatically.
  - Only the Query database step's restore is caught inside the engine; other steps' restores are deterministic and unchanged.
  - Shutting down during a restore re-query leaves the run's lock until its lease expires.
  - A restore may turn an object into an array when the row count changed.
- **The data root must be an object** for the merge. This is checked after the query has run, so the query has already been sent.
- **Phase 2 and later are NOT built and each needs its own ADR:**
  - Phase 2, write SQL: an "Allow writes" switch on each Database connection, default off; one INSERT / UPDATE / DELETE with a WHERE on updates and deletes; a row cap with rollback when exceeded; **never retried automatically**; parameters only; audit of the SQL text and the row count, never values.
  - Phase 3, an **API call step**, using the API connections of ADR 0017.
  - Phase 4, a **Send SMS step**, using the SMS connections of ADR 0018.
  - Phase 5, an **SFTP** step.

  Until then the Deliver via API and Upload to SFTP steps stay simulated, and no workflow step sends an SMS. The owner's approval of the exception covers write SQL in principle; it is recorded here but does not build or enable it.
- Not done: a schema browser or query builder, saved queries managed by administrators (Approach A, which would be safer and could still be added), stored procedures, multiple statements, caching of results.
