# ADR 0019: Query database step (read-only SQL typed by a workflow author)

- Status: accepted (implemented 2026-11-18, awaiting acceptance).
- Requested by the product owner on 2026-11-18: a workflow should be able to "call any DB ... in parallel with XML, then generate a document". The owner chose **SQL typed freely by workflow authors**, **read-only first**, and decided that **anyone who can edit a workflow may author the SQL** (no separate administrator role for it). The owner explicitly approved the **exception to the CLAUDE.md rule against author-written code**, for read SQL (this ADR, built now) **and for write SQL (Phase 2, not built)**. Design: `docs/superpowers/specs/2026-11-18-query-database-step-design.md`.
- CLAUDE.md is amended in the same change: the safety rule keeps its exception for this step only, and the approved-integrations list names it.

## Context

The Connections tab holds real database connections (ADR 0016: SQL Server, PostgreSQL, MySQL / MariaDB, Oracle) whose password is encrypted (master key `Secrets:MasterKey`) and which only run `SELECT 1` in Test connection. No workflow step used them. A common need is to take an identifier from the incoming data (an account number from an XML file), read a few fields from a bank system, merge them and generate a document. Approach B of the design was chosen: the author types the SQL in the step. It is the smallest build and the most flexible, and it is the one that runs author-written text against a database, so the guards below are the substance of this ADR.

## Decision

1. **The step.** `query-database` ("Query database"), an ordinary step with input `in` and ports `found`, `not-found` (optional to connect) and `failed`. Settings: `connection` (key of an active Database connection, picked from a dropdown), `sql` (up to 4,000 characters), `parameters` (lines `name = data.path`, names without the `@`), `resultName` (where the result goes; `iteration` is reserved), `maxRows` (default 1, 1 to 100) and `timeoutSeconds` (default 15, 1 to 60). The result is **merged into the run data** at `resultName` (the existing data is kept): **an object for one row, an array for several**, nothing for zero rows (port `not-found`). Limits: rows 1..100, time 1..60 s, and a **256 KB** cap on the serialised result. Over the cap fails with `db.result_too_large`; duplicate or empty column names fail with `db.bad_column` (a row would lose data). The field and column names used in samples and tests are synthetic.
2. **SqlGuard (the safety net, not the only one).** A tokenizer, not a regular expression, reads the SQL (strings, quoted identifiers and comments are skipped, so a keyword inside a string is fine). It accepts **exactly one `SELECT` or `WITH ... SELECT` statement** and rejects, anywhere as a bare word, write and DDL keywords (INSERT, UPDATE, DELETE, MERGE, DROP, CREATE, ALTER, TRUNCATE, GRANT, REVOKE and the like), `INTO` (`SELECT ... INTO`), `EXEC` / `EXECUTE` / `CALL`, a `;` followed by more text, PostgreSQL **dollar quoting**, MySQL executable comments `/*!`, a `--` comment not followed by a space (MySQL treats `--1` as an expression), and a **backslash inside a string literal** (MySQL escapes it, so the literal's end is ambiguous; use a parameter). Codes: `sql.empty`, `sql.too_long`, `sql.multiple_statements`, `sql.not_select`, `sql.select_into`, `sql.unterminated`, `sql.bad_parameter` (a malformed `@name`), `sql.unsupported_syntax`. The same check runs at design time (the workflow validator, and again when publishing) and **again at run time** inside the service, so a hand-edited draft or an old version cannot skip it.
3. **Values are parameters only.** The SQL uses `@name` placeholders; each name is mapped to a data path (`parameters`) and **bound as a driver parameter**, never concatenated. A placeholder without a mapping is a design error; a path that is missing or not a scalar at run time **rejects the run** with `data.query_invalid` (the data is wrong: Rejected, not retryable). Oracle uses `:name` binds, so the Worker **rewrites the placeholders to synthetic `:p1..:pN`** (by first use), which avoids Oracle's 30-character limit, reserved words and case rules.
4. **Execution guards.** Each provider runner opens the connection, starts a **read-only transaction** (SQL Server and the others through their own mechanism; `SET TRANSACTION READ ONLY` where supported) and **always rolls it back**. The command has a timeout and the reader stops at the row cap; large single values are read in bounded chunks so memory is bounded before the 256 KB cap. **Be honest about what this is:** a rollback does not undo every side effect (sequence values, calls through a linked server, some functions with their own autonomous transactions), and on SQL Server `ApplicationIntent=ReadOnly` alone does not stop a write on a plain instance. Therefore **the connection's database login MUST itself be read-only (SELECT only, on the tables the workflows need). That login is the real protection**; SqlGuard and the transaction are defence in depth. `docs/setup.md` says how to create one per provider.
5. **Where it runs.** In the **Worker only** (`Verso.Databases`, plus the SQL Server runner next to the existing probe); the API never connects. It uses the same rails as Test connection: the connection's `DatabaseConnections:AllowedServers` (a server not on the list fails with `db.server_not_allowed` before any connection), and the password is decrypted **in memory** only. No new package, no migration.
6. **Who sees what.** `GET /api/v1/database-connection-options` returns `{ key, name, provider }` of every active connection to **workflow authors and administrators** (the rest of the Database connections API stays administrators only); no server, login, database or port. **Publishing audits what will run:** `WorkflowPublished` carries `databaseQueries: [{ nodeId, connection, sql }]`, the SQL text and the connection key, **never parameter values or data paths**. The same is recorded for folder paths (ADR 0001). Column values and parameter values are never logged or audited.
7. **What the step records.** The step **Result holds only counts, column names and the duration**, never the rows, because the API returns step results to every reader of an execution. Rows live in the run's data (as any other step output) like the data they merge with.
8. **Failures.** A missing or non-scalar parameter: run **Rejected** (`data.query_invalid`). A **non-retryable** `db.*` or `sql.*` code (bad SQL, permission denied, unknown column, login failed, server not allowed, result too large) ends the run **Failed**: an author or connection problem that retrying cannot fix, so it is not retried automatically; an operator retries after the fix. A **retryable** code (timeout, unreachable, transient error) follows the normal retry policy. `db.query_failed` is non-retryable for deterministic failures (a statement that returns no columns, syntax and permission error numbers) and retryable otherwise: retrying a deterministic failure forever is worse than one manual rerun. The `failed` port exists for flows that want to handle failures themselves.
9. **Resume re-runs the SELECT.** Rows are not stored (item 7), so when a run resumes after an Approval wait or a Worker restart, the engine **runs the query again** to restore the data. The data **may differ** from the first run (a row changed or was added, so an object can become an array or a result can vanish). If the re-query fails, the run ends **Failed** and an operator retries it; it is not retried automatically.
10. **Parallel branches.** The step is an ordinary step, so it works inside Parallel branches / Wait for branches / Merge data (ADR 0009): a query on one path next to an XML parse on the other, then a merge, then Generate PDF. See `docs/samples/query-database-xml-customer.md`.
11. **Verification.** **Only SQL Server is verified against a live server** (LocalDB in the test suite). The **PostgreSQL, MySQL / MariaDB and Oracle runners are verified only structurally** (the shared helper, parameter building, error mapping), as no live servers exist yet; Oracle `LONG` / `LOB` / `NUMBER` behaviour in particular is unproven (a `LONG` column may read empty or truncated until tried on a real server). Try each type against a non-production server before relying on it.

## Consequences

- **Anyone who can edit a workflow can run a SELECT as the connection's login** on the connection's database, subject to publishing (audited with the SQL text). They can read whatever that login can read. Keep the login read-only and narrow, one connection per purpose, and review the audit trail. This is the price of Approach B.
- **The guard is conservative; it will reject some harmless SQL.** `SELECT ... FOR UPDATE` / `FOR SHARE` (they take locks), an unquoted identifier named like a write keyword (a column called `update` or `merge`; quote it), MySQL's `INSERT()` function, a backslash inside a string literal (use a parameter), and double-quoted identifiers that contain a backslash. A `#` comment in MySQL is treated as text, which is also the safe side. Rewrite the query to avoid these.
- **Oracle:** SQL that itself contains `:p1`, `:p2` outside a string collides with the synthetic names and fails with an unbound-bind error (not a safety issue). Use another bind name or a literal.
- **An empty string is a value.** A parameter whose path holds `""` is bound as an empty string, not treated as missing (the message for a missing value says "missing or empty", the check only covers absent and non-scalar values).
- **A restore failure with a retryable code is not retried automatically** (item 9); an operator retries the run. Shutting down during a restore re-query leaves the run's lock until its lease expires.
- **The data root must be an object** for the merge; this is checked after the query has run.
- Only the Query step's restore is caught inside the engine, other steps' restores are deterministic and unchanged.
- **Phase 2 and later are NOT built and each needs its own ADR:** Phase 2 write SQL (an "Allow writes" switch on each Database connection, default off; one INSERT / UPDATE / DELETE with a WHERE on updates and deletes; a row cap with rollback when exceeded; **never retried automatically**; parameters only; audit of the SQL text and the row count, never values), Phase 3 an **API call step** (using the API connections of ADR 0017), Phase 4 a **Send SMS step** (using the SMS connections of ADR 0018), and Phase 5 an **SFTP** step. Until then the Deliver via API and Upload to SFTP steps stay simulated, and no workflow step sends an SMS. The owner's approval of the exception covers write SQL in principle; it is recorded here but does not build or enable it.
- Not done: a schema browser or query builder, saved queries managed by administrators (Approach A, which would be safer and could still be added), stored procedures, multiple statements, caching of results.
