# ADR 0021: Fetch from API step (one GET through an API connection)

- Status: accepted (implemented 2026-11-20, awaiting acceptance).
- Requested by the product owner on 2026-11-20 ("Start Phase 3, the API call step"). Decisions of the owner the same day: the phase is **split**: **Fetch from API (GET)** is built now, **Send to API** (calls that change things on the other side) is a later phase with its own ADR and approval; **JSON answers only**; the branch was started from the unmerged Phase 2 branch (ADR 0020); **anyone who can edit a workflow** may author steps that use API connections. This is Phase 3a of [ADR 0019](0019-query-database-step.md); it uses the API connections of [ADR 0017](0017-api-connections.md). Design: `docs/superpowers/specs/2026-11-20-fetch-api-step-design.md`.
- CLAUDE.md is amended in the same change: the approved-integrations list names this step, and the Fetch from API step is no longer among the simulated ones (Deliver via API still is).

## Context

Since ADR 0017 an administrator can create an HTTP API connection (https base address, none / API key in a header or in the address / bearer / basic / OAuth client credentials, the secret write-only and encrypted) and press Test connection, which makes the Worker send one GET. No workflow step used it. A workflow often needs one value from outside, for example an exchange rate for an invoice, a status from an internal service, a customer's segment. The step must let an author type a **path and query values** (taken from the run data) and merge the **JSON answer** into the run data, without ever letting data steer the call to another host, without keeping the answer or the secret anywhere, and without repeating failures blindly.

## Decision

1. **The step.** `fetch-api` ("Fetch from API", category process), input `in`, ports `found` (the success exit), `not-found` and `failed` (both optional to connect). Settings: `connection` (key of an active API connection; the field uses the `api-connection` widget; existence is not checked at publish), `path` (a template up to 500 characters that starts with a single `/` and may hold `{{data.path}}` pieces, such as `/customers/{{customer.number}}/rate`), `query` (up to 20 lines `name = data.path`; names of 1 to 64 letters, digits and `_ . - [ ]`, case-sensitive, no duplicates, blank lines ignored), `resultName` (the same pattern as Query database; `iteration` is refused), `maxResponseKB` (1 to 256, default 64) and `timeoutSeconds` (1 to 60, default 15). The path and the query lines are checked when the workflow is saved and published (`config.invalid` on `path` or `query`) and again at run time (`fetch.bad_path`, `fetch.bad_query`, a definition changed outside Verso). The Worker clamps the limits again (1 KB to 256 KB, 1 to 60 seconds, at most 20 query values).
2. **What a request is.** Exactly one GET, with `Accept: application/json` and the connection's authentication (header, query key, bearer, basic, or a bearer token from the OAuth token endpoint). No body, no custom headers, no cookies, no redirects.
3. **The host cannot change.** The address is the connection's base address plus the path plus the query; the author never types a host. Each `{{ }}` piece is replaced by its value **URL-encoded as one piece** (`Uri.EscapeDataString`), so a value cannot add a segment, a `?`, a `#` or a different host. The **resolved, percent-encoded path** is at most **500 characters** (the same limit as the template and the connection's test path; encoded values grow, a Greek or Cypriot letter becomes 6 characters), otherwise `fetch.value_invalid` naming the data paths of the pieces (never a value) and the run is Rejected `data.fetch_invalid` with nothing sent; the service keeps its own check (`api.bad_request`) as defence in depth. There is no total limit on the query (at most 20 values; each value is bounded only by the data). A resolved piece that is empty, exactly `.` or `..`, or holds a lone surrogate (URL-encoding would silently replace it with another character) is refused; so is a template whose **resolved** path contains a `.` or `..` segment, even one made by a static `%2` and a value `e`. The Worker's service re-checks the path (a single leading `/`, no `?`, `#`, spaces, control characters or backslash, no dot segment raw or percent-encoded) and refuses a path starting with `//` or a query name or value that is not valid UTF-8, a query parameter that has the name of the connection's API key (kind "key in the address"), and more than 20 query values, all as `api.bad_request`. The sender then builds the address and **checks the finished object**: https, the base address's host and port, no user info, no fragment, otherwise `api.bad_request`.
4. **Values.** Paths are read with the same dotted data paths as the rest of the product (`invoice.currency`, `items[0].sku`, ...). A value must be a scalar: text, a number (invariant culture: whole numbers, exact decimals, then the round-trip form of a double) or `true` / `false`. In a query value an empty text is an ordinary value; in a path an empty text is refused.
5. **Ports.**
   - `found`: the call succeeded and there is an answer; the JSON answer is **merged into the run data at the top level under `resultName`**, the way Query database merges its rows (a field of that name is replaced; the data must be an object, else `fetch.data_not_object`). An empty array or an empty object is an answer and is `found`.
   - `not-found`: HTTP **404** (its body is never read), an **empty body** (a 2xx with no content), or an answer that is JSON **`null`**. The data is unchanged. If the port is not connected the run ends there.
   - `failed`: **only for the data's fault**: a missing or null value (`fetch.value_missing`) or an unusable one (`fetch.value_invalid`: a list or a group of fields, an empty path piece, `.` or `..`, a lone surrogate, a resolved dot segment, a resolved path over 500 characters). Nothing is sent. The step result lists issues that name data paths, never values. Unless the port is connected the run ends **Rejected** with `data.fetch_invalid` (inside a For each it rejects the whole run even when connected, as every rejecting port does; a Rejected run is not retried, the data is fixed and submitted again).
   - Every other failure fails the step with a code (items 6 to 8) and takes no port.
6. **The shared HTTP guards (ADR 0017, reused through one helper, `ApiHttp`).** https only; redirects are never followed (a 3xx is `api.redirect_not_followed`); the addresses a connection may reach are checked **when connecting** (loopback, link-local including `169.254.169.254`, unspecified and multicast addresses are refused, `api.blocked_address`; **with a system proxy this check sees the proxy's address, not the target's**, see Consequences); `ApiConnections:AllowedHosts` (when set) must list the base host and, for OAuth, the token host (`api.host_not_allowed`, before the secret is decrypted); TLS 1.2 and 1.3. At run time the stored addresses are re-validated: an address the save rules would refuse is never used, whatever `AllowedHosts` says, and for OAuth a token address that is not https, has user info or is missing is `api.bad_request` **before the secret is decrypted** (the token endpoint receives the client id and secret). **One deadline** (`timeoutSeconds`) covers the token request, the GET and the reading of the answer: a server that sends its headers and then stalls ends as `api.timeout`.
7. **The answer.** Read at most `maxResponseKB` plus one byte; a declared or actual size over it is `api.response_too_large`. It must be JSON: content type `application/json` or any `+json` type (parameters such as charset are ignored), and valid JSON (a leading UTF-8 byte order mark is accepted); otherwise `api.not_json` (a missing content type and `text/json` are refused). The parsed answer is the only place the answer exists; it is merged into the data and never logged or stored anywhere else. Engine codes for an answer that cannot be merged: `fetch.answer_too_deep` (the data would be nested deeper than JSON readers accept), `fetch.answer_unsupported` (a lone-surrogate `\uD800` escape, which .NET cannot read back); both final.
8. **Retries.** A GET is safe to repeat, so these are **retryable** (the engine's usual three attempts with delays): `api.timeout`, `api.unreachable`, `api.server_error` (HTTP 5xx), `api.rate_limited` (HTTP 429). **Not retryable** (the run fails at once; fix the cause and retry by hand): `api.token_failed` (a controller ruling: an HTTP error or an unusable answer from the OAuth token endpoint; a token endpoint that is unreachable or stalls gives the retryable `api.unreachable` / `api.timeout`), `api.unauthorized` (401, 403), `api.client_error` (other 4xx), `api.redirect_not_followed`, `api.certificate_untrusted`, `api.blocked_address`, `api.host_not_allowed`, `api.secret_unreadable`, `api.connection_unavailable` (unknown or deactivated connection), `api.not_json`, `api.response_too_large`, `api.bad_request`. `api.not_found` is not used by this step (a 404 is a success that leaves by `not-found`). `api.unreachable` is retryable as the service and sender map it; the engine's own catch-all for an exception that escapes the service (which should not happen) gives a final `api.unreachable`. Engine-side codes, all final: `fetch.bad_path`, `fetch.bad_query`, `fetch.data_not_object`, `fetch.answer_unsupported`, `fetch.answer_too_deep`, `fetch.restore`. Messages are Verso's own words for the code, never the API's text, the address or a secret.
9. **Resume re-fetches.** The answer is never stored, so when a run resumes after an Approval, a retry of a later step or a Worker restart, a step that Succeeded with `found` **fetches again** with the same path and query values (a step that left by `not-found` or `failed` changed nothing and restores nothing). **An API is not deterministic**: the later steps may see another answer than the first pass did. If the fetch fails now, finds nothing, or the new answer cannot be merged, the run fails with **`fetch.restore`** (retryable as the failure was, otherwise final); the step stays Succeeded and the run Failed, so an operator's retry resumes there.
10. **Privacy.** The step result holds `{ status, durationMs, responseBytes, connection }` only: never the path, a query value, the answer or a secret (the API returns step results to every reader of the execution). Logs carry codes and the execution's ids, not values. The request, settings and result records print `[redacted]` for the path, query, answer and secret in `ToString`, so a log line that formats one leaks nothing. As with Query database, an author can still copy fetched values into what the run records by other steps (an Archive metadata pattern, say); the step itself never records them. **Publishing audits what will run:** `WorkflowPublished` carries `apiFetches: [{ nodeId, connection, path, queryNames }]` (the connection key, the path template text, which includes its `{{data.path}}` pieces, and the query parameter **names**; the query's data paths and all data values are left out).
11. **Who may author, and the options endpoint.** Anyone who can edit workflows may use any active API connection (owner decision). `GET /api/v1/api-connection-options` (workflow authors and administrators) returns `{ key, name, host }` of every active connection for the designer's dropdown: no base path, test path, authentication, token address or secret. The rest of the API connections endpoints stay administrators only.
12. **Where it runs.** Worker only (`ApiFetchService` and `HttpApiFetchSender`, registered with the connection test's services; the API never makes the call). Same master key (`Secrets__MasterKey`) for decrypting the secret, in memory only, after the host checks. **No new package, no migration.**
13. **The designer.** The step card shows the connection and path; the connection field is a dropdown fed by the options endpoint; the path and query fields carry the hints above.

## Consequences

- **Anyone who can edit a workflow can make the Worker call any active API connection** with the connection's credentials, on any path of that host, with values from the run data. Mitigations: create connections with **read-only or least-privilege keys**, one per purpose; set `ApiConnections:AllowedHosts`; review the publish audit (`apiFetches`). A per-connection path allow-list is a possible later phase and is not built.
- **Third-party answers are merged into documents.** What the API answers can end up in a PDF, an email or the archive metadata. The template decides what is shown; treat the answer as untrusted text (values are HTML-encoded when rendered).
- **`%2F` in a value is sent as data** (`customers/a%2Fb`). A server that decodes it before routing could let a value climb out of the base path prefix of the connection. The host is still the connection's; what the call may reach is governed by the connection's login.
- **Other servers may parse paths differently** from the sender: a static `..;` segment (accepted: `;` is a legal static character and `..;` is not a dot segment), or values that produce `%5C` or `%252e`, can climb out of the base-path prefix on Tomcat / Spring-style servers (same host only).
- **With a system proxy the address guard checks the proxy, not the target.** The shared handler (`ApiHttp.CreateHandler`, ADR 0017) leaves `UseProxy` at its default (true). Behind a proxy (`HTTPS_PROXY` or the service account's proxy settings) the connect callback receives the proxy's address: the check for loopback, link-local and cloud-metadata targets and the DNS-rebinding protection then do **not** apply to the real target (the host name is still fixed by the administrator and `AllowedHosts` still applies). Run the Worker service without a system proxy for these calls, or make the proxy / egress block internal and cloud-metadata targets (`169.254.169.254`, loopback, internal ranges). **Open question for the owner:** should the shared handler set `UseProxy = false`? It would change the Test connection probe of ADR 0017 and the SMS probe of ADR 0018 too, and would stop a proxy-only network from working; not done.
- **No connection reuse:** every call builds its own handler, so a For each over many items opens a new TLS connection per item (the Test connection probe does the same).
- **A GET can still have side effects** on a badly designed API. The step cannot know. Use only APIs whose GET is safe.
- **Strict about content:** a missing content type and `text/json` are refused; XML and plain text answers are not supported (`api.not_json`); the charset is not read (the body must be valid UTF-8 JSON).
- **An HTTP error or bad answer from the OAuth token endpoint is not retried** (item 8): a token endpoint that answers 5xx fails the run until someone retries it (an unreachable or stalled one is retried).
- **An API key in the address** (the "key in the address" kind of ADR 0017) puts the key in the URL that proxies and the remote server may log; prefer a header. **HttpClient tracing**, if an operator turns it on, can log the path and query values: leave it off.
- **Resume re-fetches** (item 9): history says what happened the first time, not what a resumed run saw.
- The limits `maxResponseKB` (256 at most) and the time limit bound one call; the answer is fully read into memory up to the limit.
- **Not built, unchanged:** the **Deliver via API** step stays **simulated** (nothing is sent); **Send to API** (POST / PUT / PATCH / DELETE, a request body, headers, file upload: Phase 3b) needs its own ADR and approval; no pagination, no XML or text answers, no redirects, no per-step headers; **Send SMS** (Phase 4) and **SFTP** (Phase 5) remain later phases with their own ADRs.
- **Found while building, not part of this feature and reported to the owner (not fixed):** (a) submitting an execution whose JSON contains a lone-surrogate escape (`\uD800`) returns HTTP 500 instead of 400; (b) a Parse step reading such an escape fails as a retryable technical error (three attempts, then Failed) instead of Rejected `data.unparseable`; (c) Query database probably has the same latent merge issue for a lone-surrogate or 64-level-deep answer row (the fetch step has its own codes for both).
- The connection test's own reading of the response body (Test connection) is **not** covered by the new single deadline (pre-existing, unchanged).
- **Set `ApiConnections:AllowedHosts` in production**: with it empty any https host is allowed (the blocked addresses are still refused).

## Unverified

**Nothing is verified against a live third-party API.** The tests use a fake HTTP handler and a fake fetch service (the sender's address building, answer reading, deadline, size and JSON rules; the service's checks; the engine's ports, retries and resume). The first real check is manual, on a non-production machine: create the Frankfurter connection of ADR 0017 (base address `https://api.frankfurter.dev`), press Test connection, then run the sample `docs/samples/fetch-api-exchange-rate.md`. Not exercised by any test: a real OAuth token endpoint with this step, real chunked bodies, a real TLS failure.
